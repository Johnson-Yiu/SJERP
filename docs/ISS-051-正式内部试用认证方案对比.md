## 当前实现核查

### 登录、退出与身份状态

根 URL 仅挂载 `/admin/` 和 `/api/`；CRM API 中存在 `GET /api/session/current-operator/`，装饰为 `AllowAny`。它返回当前登录标志、角色和权限摘要，不校验密码、不创建 session，也不签发凭据。仓库没有 ERP 业务登录/退出 URL、前端登录页或退出操作。

`/admin/` 是 Django 管理站点入口。它面向 `is_staff` 管理账号，不是 ERP 员工登录流程，也没有员工账号开通/角色配置的完整业务链路。即使同域管理站点建立的 Django session 在技术上能被同站 API 识别，也不能把管理站点当作员工登录页；superuser 还会在权限函数中直接取得全模块权限。

生产阶段的 DRF 默认认证类被设置为 `SessionAuthenticationWithChallenge`，该类只为 401 添加 `WWW-Authenticate: Session`，本身不处理登录。开发阶段没有覆盖 DRF 默认认证类，因此使用 DRF 自身默认的 SessionAuthentication 和 BasicAuthentication；业务 Vue 客户端没有发送 HTTP Basic 凭据的代码。这个开发默认值不是生产登录方案。

### Session、CSRF 与请求拒绝

`settings.py` 已启用 SessionMiddleware、CsrfViewMiddleware 和 AuthenticationMiddleware，默认 API 权限类是 ModuleActionPermission。部署阶段要求关闭 DEBUG/开发超级管理员、开启 RBAC、使用 PostgreSQL；生产配置还要求 HTTPS redirect、secure session/CSRF cookie，并设定 HSTS。Session cookie 为 HttpOnly、SameSite=Lax；CSRF cookie 为 SameSite=Lax。session age、浏览器关闭策略和滚动续期没有在项目设置中显式配置，当前采用 Django 版本默认值，正式环境应由业务/运维明确接受并通过实测。

生产 API 的认证 challenge 测试证明：被拒绝的匿名业务 API 可返回 401；已认证但无模块权限的测试请求返回 403。这里的现有用例主要使用 `force_authenticate`，用于绕过真实登录过程，不能代替浏览器 session cookie、CSRF 或登录/退出验收。开发模式匿名测试中的状态码也不能直接当成生产状态码。

Axios 已声明读取 `csrftoken` 并发送 `X-CSRFToken`，但请求能否携带有效 token 取决于浏览器此前是否取得 cookie。新增登录时必须提供可靠的 token 引导，并让登录 POST 本身受 CSRF 保护。DRF 的 SessionAuthentication 只对已认证请求强制 CSRF；匿名登录请求不能只依赖它。使用 Django 标准认证函数/登录机制，并对 SPA 登录入口明确启用 Django CSRF 保护。

### current-operator、路由守卫与员工状态

前端路由守卫通过 `current-operator` 取得权限，然后决定展示业务页还是访问受限页；它当前不区分“未登录”和“已登录但无该模块权限”。加入认证后应把两者分开：401/未登录进入登录页，已登录但无权限保持 403/访问受限页。

`EmployeeProfile.user` 是 Django 用户的一对一关联；`EmployeeProfile.active` 与 Django `User.is_active` 是独立字段。权限代码在 RBAC 开启时只从 active profile 读取角色；现有定向测试验证了普通停用 profile 的客户 API 被拒绝。但该请求仍可能被 Django 识别为 authenticated，current-operator 也可能返回 `authenticated: true`。此外，`has_all_permissions()` 对 `user.is_superuser` 直接返回全权限，不要求 EmployeeProfile active。因而不能只把“停用员工”定义为关闭 profile 或移除角色。

正式账户停用应有统一、原子化的操作：关联 profile 设为 inactive、Django User 设为 inactive、撤销该用户全部已有 session，并记录实际管理员操作人；重新启用时要求重新登录。员工账号必须是普通 Django 用户，不得用 Django superuser 充当员工。默认 ModelBackend 会拒绝 inactive User；额外清理全部既有 session 可避免复用 session 的风险，尤其是后续重新启用账号时。

### 尚未被业务前端调用的认证能力

1. Django SessionMiddleware、AuthenticationMiddleware 和 DRF SessionAuthentication 已实现，但业务前端没有建立 session 的入口。
2. Django admin 提供管理站点登录；它不是 ERP 登录/退出页，且不应作为员工开通流程。
3. 开发 DRF 默认认证类包含 BasicAuthentication；前端未调用，生产配置也明确只启用 SessionAuthenticationWithChallenge。
4. `current-operator` 是被前端调用的权限状态接口，但它不是认证入口。
5. `SessionAuthenticationWithChallenge` 只定义未认证拒绝时的 challenge，不创建或结束 session。
6. 已有测试中的 `force_authenticate` 是测试工具提供的注入方式，不是业务系统可调用的登录 API。

代码和已查看的部署说明中均未发现受控 SSO、OIDC/SAML 客户端、REMOTE_USER 或可信代理身份头。现有 Nginx 示例只转发 Host、X-Forwarded-Proto、X-Forwarded-For。不得假设外部已有 IdP。

## 方案比较

| 方案 | 最小工作范围 | 部署/运营前提 | 优点与限制 |
|---|---|---|---|
| Django Session 登录（推荐首期） | 增加受 CSRF 保护的登录/退出与 CSRF bootstrap；校验 active EmployeeProfile；前端登录页、401 跳转、会话恢复和退出；统一停用及 session 撤销；明确 session 时长与登录限流。复用现有 Django User、SessionMiddleware 和部署阶段 SessionAuthentication。 | HTTPS 与同源部署优先；为每名员工创建普通 Django User 并关联 EmployeeProfile、角色及数据范围；明确密码发放、重置、离职停用、MFA 是否必需和支持责任人。 | 对当前 Vue + Django 同源 API 改动最少，不依赖未确认的第三方身份服务。Django 原生方案本身不提供 MFA/账号目录同步；如政策要求强制 MFA，应改用受控 IdP。 |
| 已有企业 SSO / OIDC 或 SAML | 接入经过批准的 IdP 回调和登出；校验 issuer/audience、state/nonce、签名和回调；把不可变 IdP subject 映射到现有 User/EmployeeProfile；未匹配或停用的身份拒绝；实现前端登录跳转及回调。当前依赖中未发现 OIDC/SAML 客户端。 | 必须由业务/IT 确认 IdP、应用登记、回调域名、密钥轮换、MFA/条件访问、人员离职同步、IdP 故障流程和测试租户。 | 集中处理 MFA、凭据和员工生命周期；改动与外部协调更大，不能在没有 IdP、claim 映射和运维责任人的情况下直接实施。 |
| 受控反向代理身份（REMOTE_USER） | 配置 Django RemoteUser backend/middleware 或 DRF RemoteUserAuthentication；映射到既有员工用户；禁用未知用户自动创建；检查 profile/User active；前端仍需认证状态守卫。 | 代理前必须真正接入批准的 SSO。应用只允许受控代理访问；代理删除外部传入的身份头后再注入身份；Django 仅信任受控 WSGI 环境/代理，直连源站不可达；退出要同时结束应用与上游 SSO 会话。 | 可复用公司已有统一认证；信任边界与代理部署配置更复杂。仅设置一个可由客户端伪造的 `X-Forwarded-User` 头不构成安全认证。 |

DRF 官方文档将 SessionAuthentication 定位为同一站点上下文内 AJAX 的会话认证，并明确提醒登录视图必须单独有 CSRF 保护；RemoteUserAuthentication 则要求服务器侧 RemoteUserBackend，且默认 backend 可能自动创建用户。因此如果选择代理方案，必须关闭未审核身份的自动建号并校验人员映射。

## 推荐方案与最小改动边界

在没有已确认 SSO 的前提下，先用现有 Django 用户和 session 做 ERP 原生登录。推荐的最小交付包括：

1. 后端添加 session 状态、CSRF token 引导、登录和退出入口。登录只接受 POST，调用 Django 的标准认证逻辑；成功后要求 User active、存在且 active 的 EmployeeProfile，并通过 `login()` 建立会话。错误信息对用户名不存在与密码错误保持一致，并增加登录限流/失败审计。退出使用带 CSRF 的 POST 并清除当前 session。
2. 加入统一员工账户停用流程：事务内停用 profile 与 User，撤销该用户所有 session；拒绝没有 active profile 的普通业务账号。保持开发身份只由 `development_superadmin_enabled()` 判定，不复制到新员工或隔离测试用户。
3. 前端添加登录页与认证状态。页面守卫先判断 `authenticated`，401 清空缓存并回登录页，403 保留为已登录权限不足；登录/刷新后重新读取 current-operator，退出后清除前端权限缓存。安全地保存/校验返回路径，避免开放重定向。
4. 账号供应可以先由受控的管理命令或受限管理员流程完成，不必为登录本身新增员工密码字段或自建密码存储。EmployeeProfile 继续只关联 Django User；不要让普通 ERP 员工成为 `is_staff` 或 `is_superuser`。
5. 明确 session 的绝对时长、空闲时长、浏览器关闭策略和并发会话策略。若接受 Django 默认期限，也应在部署验收中显式记录，不把框架默认值误认为已审定的业务策略。

基本登录/退出不预计需要新增业务数据迁移：Django auth 与 sessions 已安装，EmployeeProfile 已关联 User。实施前仍需确认目标数据库已执行 Django auth/session migrations；如选择增加身份映射或 session-version 字段，再单独评估迁移。

## 开发超级管理员与真实员工隔离测试

- 本地开发继续使用既有服务端 `development_superadmin_enabled()` 入口；不改其判定、不依赖前端 role 名称，也不把默认显示姓名写成认证或审计身份。
- 真实员工测试使用专属隔离数据库和合成 Django 用户：`is_superuser=false`、`is_staff=false`，具有关联的 active EmployeeProfile、独立角色和明确的数据范围。
- 在测试请求内覆盖设置为非开发安全模式：`APP_STAGE=staging`（或等价生产保护设置）、`DEBUG=false`、`DEVELOPMENT_SUPERADMIN=false`、`RBAC_ENFORCEMENT=true`。确认 `development_superadmin_enabled()` 为 false；不得连接生产或共享业务数据库。
- 使用真正的 Django session 登录测试（例如 Django/DRF 测试客户端登录），不要只用 `force_authenticate`。用 `APIClient(enforce_csrf_checks=True)` 或真实浏览器验证 cookie、token 和请求头。
- 隔离环境不能因用例方便而启用开发超级管理员，也不能让真实员工账号继承开发账号、角色或全部数据范围。

## 自动化测试要求

**后端认证**

- 有效凭据建立 Django session；无效凭据返回统一错误；inactive User、inactive EmployeeProfile、未关联 profile、未分配角色均不能访问受保护业务 API。
- 未登录业务请求为 401 且有 challenge；已登录但没有模块/action 权限为 403；current-operator 可读但明确返回未认证状态。
- 登录成功后的 session key 发生轮换；退出只接受 POST，退出后同一 cookie 的业务请求变成 401。
- 停用员工后，同一个旧 cookie、另一台客户端已有 cookie、附件/导出/报表等敏感入口全部拒绝；重启/重新启用账号也不得复活旧 session。
- Django superuser 管理账号与普通 ERP 员工账户分开覆盖测试；inactive employee 不得通过 profile 绑定的 superuser 获得权限。

**CSRF 与前端**

- 匿名登录 POST 无 token、错误 token 均拒绝；先获取 bootstrap cookie，再用匹配的 `X-CSRFToken` 成功登录；登录轮换 CSRF secret 后后续写请求仍正常。
- Session 已认证后的 POST/PUT/PATCH/DELETE 缺少或伪造 token 均拒绝；只读 GET 不产生业务副作用。
- 浏览器真实 session 测试覆盖直接输入受限路由、未登录被送到登录页、已登录但 403 显示权限受限、401 后状态清理、刷新恢复 session、退出及多账号切换。
- 当前不少业务测试用 `force_authenticate` 或模拟权限对象；保留这些测试做权限矩阵，但新增真实 session + CSRF 的集成测试，不能把模拟通过当成登录闭环通过。

**部署与验收**

- 用专用 staging/test 数据库验证迁移和 session 表；配置 `APP_STAGE=staging`、`DEBUG=false`、`DEVELOPMENT_SUPERADMIN=false`、`RBAC_ENFORCEMENT=true`。环境必须显式注入独立密钥、数据库、Host、媒体目录等现有必需配置，不能把测试请求发往生产。
- 使用 HTTPS 真实代理验收：代理只接受外部 HTTPS、清洗再写入可信转发头、源站不能绕开代理访问；验证 HTTPS redirect、Secure/HttpOnly/SameSite cookie、CSRF Origin/Referer 检查、正确域名和跨站拒绝。
- 如采用同源 SPA，保持前端和 `/api` 同源以减少跨域 cookie 配置；若跨域则逐项审查 HTTPS CORS origin、credentials、CSRF trusted origins、cookie SameSite/Domain，不使用通配符。
- 运行 Django `check --deploy`、认证/CSRF/RBAC 自动化、浏览器真实员工登录退出、停用与旧 session 撤销验收；运维记录 session 生命周期、登录限流、密钥轮换、日志脱敏、管理员 MFA 和恢复流程。
- 验收必须留下脱敏配置快照、测试报告和代理浏览器网络结果；不得在日志、截图或仓库记录密码、session cookie、CSRF token 或真实数据库连接串。

## 需要业务/IT 负责人确认

1. 企业是否已有正式批准的 SSO/IdP；若有，IdP 类型、员工不可变标识、MFA 策略、测试租户和负责团队是什么？若没有，是否接受 Django 本地密码作为内部试用认证？
2. 员工名册/身份源由谁维护，用户名使用员工号还是企业 UPN？谁开通、重置密码、处理遗失设备和停用离职账号，停用要求多久生效？
3. 初始员工、角色、模块权限和数据范围由谁批准？确认普通 ERP 员工不使用 Django admin/staff/superuser 账号。
4. session 的最长时长、空闲超时、浏览器关闭、共享设备和“退出所有设备”要求是什么？是否强制 MFA 或定期重新认证？
5. 内部试用部署在 staging 还是生产隔离区；同源域名、HTTPS 代理、数据库/媒体隔离、登录审计和故障联系人由谁负责？

这些决策未确认前，推荐方案只是技术建议，不能据此创建真实员工、切换环境开关或宣布正式试用已具备认证。
