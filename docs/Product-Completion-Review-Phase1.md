## 结论与边界

核心销售—采购—库存—发货—收付闭环可运行。当前主要完成度缺口在「完成一步后自然进入下一步」、长列表的定位能力、已存在的实际装箱 API 无 UI，以及跨页面工作上下文保留。审查按 5–20 人团队的日常效率衡量，不建议现阶段建设集团级审批和治理框架。

方法：检查 `frontend/src/router.js`、各页面和弹窗、`backend/crm/{models,serializers,views,urls,context}.py` 及相关服务；用**内置浏览器只读**访问 25 个顶层页面和代表性的订单工作台，并以源代码核对嵌入式业务入口。没有提交业务数据、执行删除或重放完整 Formal UAT。以下「风险」是产品使用风险，不等于已复现的数据错误；未实际操作的交互判断标为代码审查，不冒充 UI UAT。未覆盖移动端、真实 20 人并发、生产数据规模和所有错误注入路径。

统计口径：25 个顶层页面 + 5 类嵌入式工作台/抽屉，按下表 **9 个模块组** 汇总；PCR 共 **20 项**：P0 0、P1 0、P2 12、P3 5、Enhancement 3。后端已有而前端完全缺失/未接入 **3 项**（PCR-007、008、009）；Workflow **9 项**，UI/UX **7 项**，Feature Gap **4 项**。分类互斥，优先级与类别分别计数。Phase 建议：P2-Next（下一轮产品优化）、P3-Later、Enhancement-Review。无已证实数据破坏风险。

## 工作流与分支审查

主链路 `Lead → Customer → FollowUp → Quote → Order → 库存/采购 → Receipt → Inventory → Shipment → Payment → Completed` 有可运行路径。Quote Accepted → Order 和 Order 缺货 → 采购草稿已有入口；订单工作台显示可用/出库/回款。体验断点是 FollowUp 完成后创建报价不够就地、采购到货后回销售订单靠记忆、订单出库后要去财务页人工找关联计划、回到列表时工作筛选丢失。需要的是上下文导航和明确 CTA，不是重建流程引擎。

高级分支：现有库存、部分库存+采购、多个供应商、部分/多次收货、部分/多次发货、定金+尾款、多笔收付、运费/折扣、交易单位及一采购单分摊多销售订单已有业务实现并通过 Formal UAT。产品层面多 SKU/多次发货逐行操作增加工作量（PCR-006），收货后缺明确「继续履约」入口（PCR-004），财务记录回合同较费力（PCR-005）。这些是交互效率发现，不宣称计算错误。

## CRUD、快照、语义与剩余验证

已见重要业务记录采用确认、取消、冲销、作废或修订：订单/采购仅草稿可删，财务流水作废、库存手工流水和收货可冲销；这比一律直接 Delete 更符合追溯。主数据仍有 CRUD，但重要外键多为 `PROTECT`，不要把其普通删除按钮等同于已证实数据破坏。需要在后续独立审查专门核对产品参数/证书及主数据删除提示是否足够解释依赖关系，本轮不报 P1。

报价保存 `buyer_company_name`，报价/订单/采购行有 SKU 名称、型号、单位及供应商等快照，预计装箱与流水亦存关键快照。**明显待核验边界**：`Order` 本体只关联 `Customer`，未见独立买方公司名快照；订单列表/工作台使用当前客户名。客户改名后旧订单展示可能随之变化，但 `PROTECT` 防删除，且报价/PI 快照另有机制。此处是历史展示口径核验点，不能仅凭模型定性为 P1 或破坏；建议独立审查用只读历史样本/隔离测试确认合同展示预期。

Formal UAT 覆盖核心闭环，不等于覆盖所有可用 API。最显著的重要能力空白是**实际 ShipmentPackage UI**（PCR-007）：模型/API 已在，预计装箱与真实箱单语义不同，现有 PASS 不能替代实际装箱的 UI 验收。若业务实际不维护箱单，则保留后端能力、不急于上线 UI；若需向客户/物流输出实装信息，应先定义需求后单列 UAT。其余发现以效率和理解为主，没有证据显示历史 P1/P2 回归。
