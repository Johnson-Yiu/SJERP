## 3. 三类统计边界与日期

| 口径 | 允许的来源 | 何时计入 / 不得混入 |
|---|---|---|
| 人民币实际资金流 | 已确认银行结汇人民币到账，以及按批准标准确认的CNY直接收付/费用资金事实 | 按批准的银行发生/入账日期；不从外币×汇率自动补值，不等于销售收入、利润或账户余额 |
| 原币业务辅助账 | 既有Transaction、PaymentPlan、AdvanceAllocation、合同 | 客户原币已付款即可按原规则核销，结汇前后应收不二次变化；不同币种不直接相加 |
| 人民币参考折算 | 历史rmb_amount、原币×流水汇率、应收应付×合同汇率、合同及预计成本利润 | 标明“折算参考”与来源日期；不能与实际资金数字相加，也不能称已银行到账 |

建议新指标称“人民币实际流入 / 实际流出 / 净流量”，不要称“实际销售收入”。结汇增加人民币资金、减少外币资金，属于币种转换；在人民币资金视图列入到账，在全币种经营外部收入视图不能再增加一笔销售收款。没有期初、完整资金变动及账户核对，不提供“真实银行余额”。

金额为0与未核实必须分开：已确认事件汇总可为0；未接入/来源未知/期间资料不完整用null、待核对或明确coverage说明，不把未知银行余额或未知历史实际收入填0。建议响应携带basis、version、date_basis、coverage_status、coverage_since和未核实记录数量；数量也须权限过滤。统计已确认子集时必须标注“仅已核实记录”，不能暗示覆盖全部历史。

外币直接支付供应商仍保留原币已付和人民币参考值；没有对应CNY扣款事实就不能凭外币付款折算制造人民币实际流出。若另行购汇发生CNY扣款，应引用该银行事实，不能再叠加原外币付款折算。购汇/跨币付款闭环是否纳入范围仍须D06/D07决定。

当前`rmb_amount or ...`把零值当缺失是既有审查ISS-105分支；本轮仅源码核实，不推断真实损失。新实际资金字段未知时不得回退到参考折算，已确认金额0也不能触发这种回退。

结汇次月到账时，原币收款仍归原日期，新实际人民币归银行日期；同期间图表不可混用交易创建时间。差错冲销是否回溯原期间见D04，确认前同时保留原发生日期与更正日期，不能偷偷重写已导出期间。

## 4. 最小可行方案：两个增量模型，不建完整外币总账

建议沿用既有审查“资金事实+来源分配”的两表结构，收窄到本轮人民币资金需求，暂名`RmbCashEvent`和`CashSourceAllocation`。它们不替代Transaction，也不新增第二套应收/应付核销。名称及字段规格待设计复审；本轮无DDL或migration。

### 4.1 资金事实 RmbCashEvent

- 唯一事件ID/编号、稳定request_key、规范化请求内容摘要、类型（结汇到账/CNY直接收付/单独费用/更正）、CNY方向、银行发生日期、确认状态、凭证来源、银行参考号、受控账户别名及必要尾号。不得保存网银凭据或把参考号文本当作已对账证明。
- 银行实际净到账/实际扣款为权威CNY事实。结汇另记实际含扣CNY费用；毛额可由净额+含扣费用派生，若凭证也提供毛额，确认时严格校验三者相等并保存原凭证。不能用汇率重算覆盖净到账。独立扣费用独立费用事件，不能同时当含扣费。
- 银行报价汇率可选保留6位，实际毛额/净额隐含汇率分别只读派生并标明分母/口径；来源原币总额由有效分配行求和，不再存一个可不同步的“可结汇余额”。
- 确认后的金额、来源关联和凭证快照不可直接改删；更正采用反向记录/替代关系、原因、时间与版本。状态标识是否已被冲销可以更新，原金额字段及原事实保留。开发默认身份不冒充真实员工签字或正式审批。

### 4.2 来源分配 CashSourceAllocation

- 事件→具体Transaction现金行，保存本次使用原币金额、来源币种/来源账户确认信息及分配依据/策略版本；一个事件多行、一个来源多事件，天然支持合并与分次结汇。
- 来源按具体根/拆分行列举，每行金额只计一次；root是业务请求家族入口，不代表root.amount等于整笔银行收款。跨分期30+70的原收款可合计100，但不能再把root作为100额外加上。
- 原币可结汇量=已核实来源现金量−有效结汇占用−已明确归属的同币种退款/其他实际消耗。**不减AdvanceAllocation.allocated_amount**，也不以PaymentPlan.remaining_amount为上限；它们表示债务核销，不表示外币现金剩余。
- 现有退款关联计划、未完整关联原收款；银行资金又可能混用，不能假定所有退款来自某个root。存在来源不明退款/历史已结汇/未核对账户时，显示“可结汇额度待核对”，不自动放行。MVP可先拒绝这类自动确认并要求来源确认；最终匹配策略由D06决定，不能用备注、等金额或任意FIFO猜测。
- CNY直接收付款可在同结构下关联既有CNY现金家族并确认一次，不强制走结汇。历史CNY流水即使rate=1，也不能不经D02定义的确认条件就整体认证。
- 结汇人民币按来源的分析分摊仅在确需订单/客户归属时生成，按事件实际总额及稳定规则守恒；它不新增现金。分摊快照不能因后续AdvanceAllocation变化自动重分，归属改动另留版本。

### 4.3 MVP明确暂缓

不建完整外币总账、复式凭证引擎、自动汇兑损益、实时汇率、银行自动导入或完整BankAccount余额系统。先保存受控账户标识与凭证来源；同一结汇批次只接受一个已确认外币来源池及一个CNY到账池。跨银行、混币、外币手续费、购汇支付的自动化另经授权；存在这些记录时明确拒绝或待核对，不静默丢弃。

账户别名不能证明期初/余额。若业务要求按银行账户出余额或不同账户内部转账统计，才增轻量BankAccount及期初对账；不在本轮预设必须增加第三张主档表。

### 4.4 原子性、幂等、作废与权限作为首发门槛

确认服务一次事务：校验财务权限/来源范围→按稳定顺序锁来源及占用→重算额度/费用→校验银行事实→写事件和分配→提交。任一失败全部回滚。两个不同request_key并发占用同一来源，也不能超额。request_key同内容重试返回同事件；不同内容返回冲突，不能把唯一约束拒绝直接当成功。银行参考号是否具有唯一性需验证，不以“同金额/同日期”去重真实两笔付款。

保存中禁止关闭/重复提交；响应丢失时按稳定编号回查，保留输入和错误，刷新/重开恢复策略须另行实现，不能把FUP-01同表单编号保护夸大为已具备全站幂等。

原币流水已有有效结汇依赖时，作废不能只恢复计划而遗留实际资金。建议MVP先明确拒绝带有效结汇依赖的原流水作废，要求按已批准更正流程解除；真实银行未撤销的到账不能因业务流水误录就虚构一笔银行退款。退款、来源调整、历史补证也必须检查依赖；解除方式、统计更正日期及已结汇后退款见D04/D06。安全拒绝本身也要回归“余额、来源额度和资金事实均不变”。

读、搜索、来源候选、详情、预览、确认、冲销、导出和凭证访问均复用现有模块权限、finance_scope及development_superadmin_enabled()。合并批次涉及不可见来源时，建议先按现有拆分家族策略整体隐藏/拒绝；不得只截掉来源行却保留全批总额供反推。不是启用正式RBAC，也不创建员工测试账号。

## 5. 场景与防重复核对

以下均为设计验收样例，非本轮真实业务操作。

| 场景 | 拟议处理 | 必须成立的不变量 |
|---|---|---|
| A 收外币、未结汇 | 只登记原币收款，按原规则核销；显示原币已收、参考折算与待结汇/待核对 | 新CNY到账事件为零条；人民币全量事实未知时标资料未齐，不能宣称实际银行收入为0 |
| B 即收即结汇 | 先引用已成功的收款家族，另确认银行事件；可同屏分两步，失败后只重试未完成一步 | 不重复customer_receipt、不再次调用原币核销；不因结汇失败重建收款 |
| C 一笔分多次 | 每次独立银行日期/实际金额，来源分配累计不可超可用量 | 第一次60、第二次40使用100；超额和并发第二次失败无部分写入 |
| D 多笔合并 | 同币种/已核实来源池多行组成一结汇事件 | 现金按事件一次；来源分配不是第二次现金；不同客户不互相核销应收 |
| E 含扣/另扣CNY手续费 | 依银行凭证区分；净到账与费用说明同源 | 净额已扣费时不再扣一次；另扣费用真实发生才计单独流出；已有bank_fee不得再自动生成第二笔费用 |
| F CNY直接收付款 | rate=1，按D02证据标准确认既有现金记录与资金事件关联 | 同一事实只计一次；不把Transaction整表与新事件再相加 |
| G 历史来源未知 | 保留原金额为参考，追加补证关系；无证据不认证 | 不改旧金额、不自动结汇、不自动补计划，不把未知当已确认零 |
| H 已结汇后客户退款 | 辅助账退款仍按合同币种；实际资金来源与退款资金事实另核对 | 不能把原结汇到账直接删掉；不能允许外币来源超占用；跨币退款换算/购汇规则未定则不自动执行 |

合成对照：原币USD100，参考汇率7.000000→参考CNY700；银行结汇毛额710、含扣费5、实际净到账705。人民币资金净额取705，既不取700，也不将700+705=1405；若净705再减手续费5，则错误变700。若银行实际是先入710、再单独扣5，两笔事件净额仍705。毛流入/费用拆列选择需D01批准。

## 6. 拟议精度、汇率与舍入规则

这些是待复审的技术政策建议，未改变当前4位规则。

| 对象 | 推荐规则 | 历史兼容/拒绝原则 |
|---|---|---|
| 新银行实际CNY金额 | 2位，Decimal字符串输入，事实校验不经过float | 过多有效小数拒绝并提示，不能自动把银行凭证金额改成别值；“未知”用独立状态/空值，确认零与未知不同 |
| 新实际原币收付/结汇使用量 | 配置币种最小单位；拟CNY/USD/EUR/GBP/HKD/AUD为2位、JPY为0位 | D05批准币种表后采用；不支持币种拒绝，不能默认全币种2位 |
| 存储 | 新CNY事实可用DecimalField(18,2)，来源使用量保留至少旧4位承载能力；新输入按版本校验最小单位 | 不把旧Transaction/PaymentPlan/AdvanceAllocation列缩到2位；4位存储不等于允许所有新银行输入4位 |
| 汇率 | 延续6位及“1原币=CNY多少”方向，CNY=1；显式有限正Decimal校验 | 银行原始报价若超6位应保留凭证并提示，不静默截断。实际净额不由汇率回算覆盖；隐含毛/净汇率可展示6位 |
| 计算入账与分摊 | 批准的计算结果显式quantize(币种单位, ROUND_HALF_UP)，先确定事件总额再分份额 | ROUND_HALF_UP半值远离零；费用方向单独存，不用正负舍入混淆方向；冲销精确反向引用旧份额 |
| 单价/成本/数量 | 保持既有业务必要精度，单价/单位成本可12位，数量按基础/交易单位既有约束 | 不为“财务2位”连带改库存换算、单价或报价成本 |
| API/前端/CSV | 金额返回字符串及币种、口径/精度版本；前端只显示，服务端Decimal做等式与额度判断 | 当前Number和formatMoney两位显示不代表原始数据只有两位；历史精确值提供明细查看，CSV不丢历史4位 |

复用与收敛：quotation_export_dto.py:46、quote_export.py:47、quote_xlsx_renderer.py:63已有展示用ROUND_HALF_UP；purchase_costs.py:72已有固定CENT分摊。建议将被批准的币种单位校验/量化抽成一个共享入口，并由现有调用逐项委托，不另建多套CENT工具。报价展示和采购成本工具不直接当正式资金入账工具；finance目前quantize未显式rounding，不能用全局切换Decimal上下文来影响历史全系统。

本轮纯Decimal合成验算（未运行Django、未访问数据库）：

- 当前默认上下文ROUND_HALF_EVEN；旧路径12.34×7.123456=87.90344704→4位87.9034，2.34×7.123456=16.66888704→4位16.6689；新展示2位可为87.90/16.67，旧存储不能改成这两个数。
- 显式ROUND_HALF_UP：1.005→1.01，-1.005→-1.01。
- 两笔0.01×1.005000分别按当前4位舍入相加为0.0200；整笔0.02折算后为0.0201。说明来源拆分参考值不应代替银行事件总额；不是已发现真实损失。
- 最小单位分摊按稳定顺序分配尾差，例如0.01分三份为0.01/0/0，总额严格守恒；零份额可以是分摊结果，但实际零收付是否可确认为事件仍受D05规则控制。

## 7. 四位历史数据风险与保护

| 风险 | 为什么不能直接改2位 | 后续获授权核实/处理 |
|---|---|---|
| 原币金额4位、核销4位 | 计划已核销/余额、预收可分配额及退款上限可能被舍入改变 | 脱敏盘点非最小单位尾数及计划等式；历史按旧版本精确保留 |
| rmb_amount4位 | 折算公式有真实4位结果，但不能证明银行事实 | 保留参考值；按凭证追加银行事实，不以新舍入覆盖原值 |
| 一笔拆多行 | 逐行舍入≠总额舍入；只看root也可能漏尾款/超额 | 家族整体盘点、每行额度及总额守恒，不能重新分配历史流水金额 |
| 0.0001等残余 | 两位收款可能无法精确结清旧计划 | 标历史精度待核对，尾差核销/豁免必须D05决定并另建有依据调整；不得自动补收、清零或认定已结清 |
| 旧前端/serializer两位显示 | 页面0.00不证明数据库0；导出、计划、订单摘要可能显示精度不同 | 先核实精确API/DB，提供历史原始值，不能根据截图金额反写 |
| 退款、作废和预收 | 新舍入重算旧反向金额会破坏原分配/额度 | 旧反向沿旧精度及快照处理；跨版本新分配需兼容验证，不整体冻结所有合法历史操作 |
| 日期/来源/归属不明 | 币种、rate=1、reference、confirmed均不能代替补证 | 资料未知保留UNKNOWN；只追加确认及来源关系，未确认不进完整实际资金口径 |

本轮历史受影响行数、金额、币种分布、银行是否已实际结汇、历史覆盖起点均UNKNOWN，未读取业务库。后续盘点先批准数据范围，用只读事务/只读账户执行聚合计数与校验，不导出客户姓名、银行号或完整财务明细；保留脱敏结果和工具版本。需要迁移时先备份、dry-run、验证行数/原币/核销/库存不变及可恢复性；只增加新表/关联/索引，禁止降精度或批量UPDATE旧金额。回滚停用新读口径，不删除已确认事实。
