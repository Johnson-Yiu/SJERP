# SUNJACK-ERP 持续审查协议

本协议与 `AGENTS.md`、[`PROJECT_ISSUES.md`](PROJECT_ISSUES.md) 和 [`PROJECT_PHASES.md`](PROJECT_PHASES.md) 一同生效。目标是让后续每轮都从当前仓库与可验证证据出发，保留历史缺口，不把测试通过或旧报告当作全站验收。

## 每轮开始

1. 读取 `AGENTS.md`、`docs/PROJECT_ISSUES.md`、`docs/PROJECT_PHASES.md` 和本协议；再按本轮范围读取对应业务规则、历史 UAT、风险与审查文档。
2. 核对用户指定基线、当前分支/HEAD、工作区和最新远端状态。已有工作区内容应保留；不要通过清库、重置或改写远程历史来准备测试。
3. 确认用户授权的工作边界。开发阶段继续使用服务端 `development_superadmin_enabled()` 的既有机制；除非用户明确进入内测/上线，不启用正式 RBAC、不降权开发人员、不把默认开发身份伪造为真实账号。
4. 先列出风险/业务权限矩阵和验收场景，标出关联模块、数据范围、读写/导出/附件入口、正常路径和拒绝路径。旧文档的 FAIL 需要查后续修复；旧文档的 PASS 也不替代当前场景验收。
5. 涉及真实业务数据时使用隔离数据库和标记数据；未经明确授权不得清空、批量改写或删除已有业务记录。文件操作遵守浏览器和工作区安全限制，不尝试绕过。
6. 用户已明确授权一条包含多个 Part 的工作路线时，完成当前 Part 的验收后可以在路线内自动进入下一 Part；不得超出授权路线、进入用户明确排除的 Part。进入内测、生产部署或改变重大业务规则，无论是否已列入路线图，均须用户明确授权。

## 问题台账维护

- 新问题使用从 `ISS-001` 起连续递增、永不复用的 ID；来源要精确到文档章节、测试、API/页面、对话或提交。每项必须记录首次发现来源与日期、最近核实情况、优先级、受控状态、影响、职责负责人、明确的下一步动作、计划阶段和可复核的验收/关闭依据。日期、SHA、CI 或来源无法确认时写 `UNKNOWN`，不得推测或编造。
- ChatGPT 在对话或独立审查中发现、但 GitHub 尚无问题记录的事项，必须在下一轮工作提交中补入台账；包括文案问题、待核实问题和业务待决事项。保留原始对话/审查来源，无法确认首次发现日期时写 `UNKNOWN`。
- 每个未关闭 Issue 必须有明确可执行的下一步；`BLOCKED` 项写明解除阻塞所需的业务决定、授权或外部证据，`NEEDS_VERIFICATION` 项写明核实入口和证据。暂不排期时也记录下一步如何作出排期或不做决定。
- 旧问题只凭旧文档不能认定仍存在；查明后更新为 `CLOSED`、`FIXED_PENDING_REVIEW` 或 `NEEDS_VERIFICATION`，说明后续证据。新报告指出本轮未测时，准确记录是“该轮未覆盖”，不可覆盖更早有效复测，也不可把历史 PASS 扩大为全流程 PASS。
- 状态只用 `OPEN`、`BLOCKED`、`NEEDS_VERIFICATION`、`FIXED_PENDING_REVIEW`、`CLOSED`。延期事项用 `BLOCKED` 并写明“延期”和解除条件；业务待决不能由开发者猜定。
- 只有问题确已解决、所需正常与拒绝路径回归通过、证据可定位，并由独立 ChatGPT 复审或用户明确接受后，才可标记 `CLOSED`。Codex 不得自行关闭已等待复审的项目；代码合入、CI 通过或阶段 PASS 均不自动关闭历史遗留。
- 数据模型无法表达授权，或修复要求大规模迁移/改变共享采购、财务、库存业务边界时，先登记 `BLOCKED` 和所需业务决策；继续做权限边界明确的独立修复。
- 阶段或 Part 切换时，`BLOCKED` 和 `NEEDS_VERIFICATION` 必须继续留在台账；只有逐项依据新证据和关闭协议更新后才可改变状态。不得因阶段切换、PASS、未复现或旧记录未被本轮提及而自动清除。

## 每轮验收与报告

1. 根据风险选择必要的自动化测试、Backend/Frontend/PostgreSQL CI、浏览器 UI、真实 HTTP 状态/响应和实际文件内容检查。权限安全不能只看 UI 隐藏；列表、详情、搜索、嵌套 Context、导出、动作、附件直链都要覆盖适用范围。
2. 正常业务成功路径与拒绝/失败原子性都要验证。报告测试的数据库、身份、数据集、命令、精确 HEAD 和运行链接；未运行项写 BLOCKED 或 NEEDS_VERIFICATION，不推测结果。
3. UI/UX 改动需遵循 `AGENTS.md` 的真实 Chrome、自动回归和可见文案检查要求。浏览器拒绝截图导出时，严格遵守限制，记录可核验替代证据与视觉复核限制，不虚构截图。
4. 结束时更新问题台账和阶段计划，并报告：新增问题、修复但待复审、关闭及其独立审查依据、仍未关闭、BLOCKED/业务待决、延期和本轮未覆盖事项。更新统计数并复核每个 ID 恰计一次。
5. 向用户交付精确提交 SHA、对应 CI、测试结果、证据路径和风险。若本轮只做文档，明确说明业务代码未变；不得以此宣布产品/阶段封版。

## 独立复审

交付后等待 ChatGPT 或用户进行独立复审。发现复审意见时，逐条绑定台账 ID，区分事实错误、修复缺陷、证据不足和业务决策；按授权范围处理。复审结论只关闭明确接受的条目，不影响其他历史事项，也不隐含开始下一阶段。
