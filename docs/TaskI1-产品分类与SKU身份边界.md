# Task I1：产品、分类与 SKU 身份边界

## 目的

产品分类和分类参数是产品的默认参数模板；SKU Code、当前销售型号，以及已写入报价、订单和采购单的快照则是不同层级的业务事实。Task I1 的目标是在这些边界之间明确哪些变更可以直接发生，哪些必须经由可预览、可确认的正式流程发生。

## 冻结前后的分类模板

存在 SKU 但尚无已发布 `SKUParameterPlan` 的产品属于历史或过渡状态。它仍会读取分类模板，因此会阻止会改变 SKU 身份结构的模板操作：删除参数、修改 SKU/销售型号参与规则、必填规则、单位、默认值，或新增会参与 SKU/销售型号/必填的参数。接口会返回受影响产品清单。

在产品发布当前 SKU 参数方案后，方案成为该产品的参数结构快照。后续分类模板变更不会自动改写该产品现有 SKU 的参数、SKU Code、显示名称或销售型号。若业务需要把新模板应用到 SKU，必须在产品的 SKU 参数方案中分析并发布。

普通可选属性可以在未冻结范围中新增，因为它不会进入 SKU 身份；同级分类排序也不改变继承关系，因此允许直接调整。

## 不可直接改变的模板结构

- `CategoryAttribute.key` 是稳定参数标识，创建后不能修改；业务含义变化时新增参数，再通过 SKU 参数方案处理。
- 参数所属分类不能迁移，参数排序必须使用分类参数的预览/确认排序操作。
- 有子分类、主分类产品或附加分类产品关联的分类不能删除。
- 有未冻结 SKU 参数方案的产品时，不能直接调整该分类及其子树的父级关系。
- 有未冻结 SKU 参数方案的产品时，不能直接修改该产品的主分类或附加分类。

分类参数页面会提示：模板变化不会自动影响已有已发布参数方案的产品。

## SKU 身份与 Sales Model Prefix

SKU Code 创建后永远不改。已有 SKU 的产品也不能通过普通 `PATCH /products/{id}/` 直接更改 `sales_model_prefix`。

销售型号前缀改动必须使用两步流程：

1. `POST /products/{id}/sales-model-prefix-preview/` 根据当前有效 SKU 参数和缩写计算拟变更的销售型号，并返回基线、受影响 SKU 与冲突。
2. `POST /products/{id}/sales-model-prefix-apply/` 提交同一前缀与预览基线。在一个事务中锁定产品和有效 SKU，重新计算并校验冲突，再写入新前缀和当前 SKU 销售型号。

应用时会为每个变化的 SKU 保存 `SKUVersion`，SKU Code 不变。任何冲突或基线过期都会使整个事务失败，不会留下部分更新。

历史 Quote、Order、PurchaseOrder 明细的 SKU Code、Sales Model、名称和描述快照不会被上述操作改写。

## 产品客户统计

产品客户历史只统计 `confirmed`、`production`、`shipped`、`completed` 的订单；草稿和已取消订单不是正式销售事实，不进入统计。
