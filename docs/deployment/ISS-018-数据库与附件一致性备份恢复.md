# ISS-018｜数据库与附件一致性备份恢复运行手册

本文件是部署前的运行手册和隔离演练边界，不代表已连接生产服务器、修改生产权限或部署定时任务。它与 ISS-047 的私有 `MEDIA_ROOT`、ISS-051 的环境隔离和 ISS-043 的审计备份要求一起使用。

## 当前架构审查结论

当前仓库的目标拓扑仍是单服务器：

```text
Nginx（只代理认证 API）
        │
        └── Gunicorn/Django ── PostgreSQL
                    │
                    └── 独立持久化私有 MEDIA_ROOT
```

仓库提供两条不同的维护路径：`create_consistent_backup` / `restore_consistent_backup` 用于文件型 SQLite；`backend/operations_backup.py` 调用 `MaintenanceBackup`，用于经目标身份校验的 PostgreSQL 17 与私有媒体联合备份/隔离恢复。后者需要独立维护登录、pgpass、只读媒体栅栏、精确数据库系统标识和候选代码 SHA。仓库不含已配置的生产主机、Nginx、systemd 定时器或异地存储。本轮没有目标 PostgreSQL 连接信息，生产调度、目标 ACL/代理、异地副本和 RPO/RTO 仍为 `DEPLOYMENT_VERIFICATION_PENDING`。

## 一致性契约

不能把独立的 `pg_dump` 和独立的文件复制结果直接称为同一恢复点。本实现采用以下可核对契约：

1. SQLite 路径要求运维先停止 ERP 写入，并显式传 `--quiesced`。PostgreSQL 路径使用专用维护身份、拒绝其他可写登录/活动写会话，锁定公开表并导出 PostgreSQL 17 快照；私有媒体还须通过操作系统只读栅栏。进程内媒体锁本身不证明其他进程停止写入。
2. 在一致性窗口内建立数据库快照，再复制 ISS-047 私有媒体清单中的每个文件和目录；复制后重查媒体栅栏与清单，任何变化都会丢弃整个归档。
3. 数据库快照、媒体目录、恢复配置白名单、SHA256 清单和一致性元数据进入同一个 ZIP 归档。归档完成后再做 ZIP CRC 和归档 SHA256 校验。
4. 恢复必须使用不存在的新隔离目录；先在目标目录同一文件系统的临时目录完成解包、数据库 SHA256、SQLite `integrity_check`、媒体逐文件 SHA256 和配置 SHA256 校验，全部通过后才用原子重命名切换到正式目标。已有目录（包括空目录）一律拒绝，不删除非空目录，也不留下半成品正式目标。
5. 清单只保存 `MEDIA_ROOT` 相对路径、大小和 SHA256；不保存绝对服务器路径、密钥、数据库连接串或真实凭证。

## 私有媒体目录与活动内容

新清单同时记录 `directories`、`files`，媒体摘要覆盖两者。归档显式保留 `media/` 根及嵌套空目录；旧版没有目录清单的归档仍按文件清单验证。恢复先校验所有成员路径、ZIP CRC、数据库/配置摘要和媒体逐文件 SHA256，再提交到全新的隔离目标。POSIX 恢复媒体目录使用 `0700`、文件使用 `0600`；Windows 生产 ACL 仍须单独核验。

私有文件访问继续经授权 API 并绑定其业务记录。响应只允许通过实际字节识别且可解码验证的 PNG、JPEG、GIF、WebP 内联预览；SVG、HTML、文本、PDF、未知或损坏类型都以 `application/octet-stream` 和 `Content-Disposition: attachment` 返回，带 `nosniff`、私有缓存、同源资源策略和 CSP sandbox。历史文件在读取时同样执行该规则，不依赖上传 MIME 或扩展名。银行凭证继续使用现有来源绑定、大小/SHA256 验证和原文件名下载。

## 备份文件访问控制

备份归档、加密副本、SQLite 恢复文件、恢复媒体和结构化结果都属于敏感文件：

- POSIX 新建备份目录使用 `0700`，目录内文件使用 `0600`。已有备份目录如果组用户或其他用户具有权限，默认拒绝写入；运维完成所有权检查后才可显式使用 `--tighten-permissions` 收紧到 `0700`。归档输入若不是 owner-only 权限也会拒绝恢复。
- 归档临时文件、状态报告和恢复结果通过 owner-only 临时文件再原子替换，避免默认 `umask` 使敏感内容以组/其他用户可读模式落盘。恢复失败的默认报告写在目标目录旁的隐藏文件（例如 `.20261027.restore-result.json`），不会修改冲突目标；也可用 `--result-file` 指定外部报告路径。
- Windows 上应用代码不会把 `chmod` 当作 ACL 隔离。生产/预发布必须由部署人员在 NTFS 上预置并核验 ACL：仅授权服务账号和明确的备份运维账号可访问，移除 `Users`/`Everyone` 继承读写权限，并用 `icacls <backup-path>` 或等价受控工具保存核验记录。未有该证据时命令在部署阶段 fail-closed，开发 Windows 结果只标记 `WINDOWS_ACL_PENDING`。
- 备份根目录及恢复父目录必须位于受控私有卷；本手册不开放 `MEDIA_ROOT`，不生成游客链接，也不修改真实生产 ACL。

FIX-02 对恢复报告路径执行原始路径安全检查：在任何 `resolve()` 前拒绝符号链接；报告路径不得是恢复目标本身，也不得位于目标目录内部。默认报告使用目标目录旁的隐藏路径。恢复成功提交后，结构化结果中的 `status`/`restore_status` 表达恢复是否完成，`report_status`/`report_error` 单独表达报告写入是否成功；因此报告落盘失败不会把已经完成的恢复误报为未恢复。

`prune_erp_backups` 在进入权限检查前拒绝不存在、非目录或符号链接的备份路径，不会为清理命令自动创建目录。显式 `--tighten-permissions` 的既有权限收紧语义、默认 dry-run 和 7/4/3 保留策略不变。

`create_consistent_backup` 只接受文件型 SQLite；遇到 PostgreSQL 会 fail-closed。PostgreSQL 请使用独立入口和受限配置文件：

```text
python backend/operations_backup.py backup --config /etc/sunjack/backup.json
python backend/operations_backup.py restore --config /etc/sunjack/restore-drill.json
```

备份配置参照 `docs/deployment/operations-backup.example.json`，必须指向经核验的 PG17 实例、独立维护账号/passfile、媒体只读挂载和新归档路径；恢复配置提供原归档、该归档 SHA256 和一个已有的受控恢复父目录。恢复器创建随机数据库及私有媒体目标，不覆盖现有数据。须在隔离目标检查业务表状态、附件引用/大小/SHA256、迁移状态和媒体权限。目标的数据库主机、TLS CA、系统标识、写入者静默和只读栅栏均不可用示例值替代。

## 本地命令

```text
python backend/manage.py create_consistent_backup \
  --database /srv/sunjack/isolated.sqlite3 \
  --media-root /srv/sunjack/private-media \
  --output-dir /srv/sunjack/backups/local \
  --backup-id 20261027T020000Z \
  --quiesced \
  --status-file /srv/sunjack/backups/status/latest.json

python backend/manage.py restore_consistent_backup \
  --archive /srv/sunjack/backups/local/erp-backup-20261027T020000Z.zip \
  --target-dir /srv/sunjack/recovery-drill/20261027 \
  --result-file /srv/sunjack/recovery-drill/20261027-result.json

python backend/manage.py prune_erp_backups \
  --directory /srv/sunjack/backups/local
```

`prune_erp_backups` 默认只生成保留计划；确认副本已复制到独立故障域后，运维才可在目标环境显式增加 `--apply`。策略按归档元数据保留最近 7 个日备、最近 4 个周备和最近 3 个月各一个月备，层级取并集，并同步清理同名 `.age` 副本。

恢复重试必须换用新的不存在的 `--target-dir`，或先由授权运维按部署策略处理旧的隔离目录；应用不会删除非空目录，也不会把失败报告写回冲突目录。

## 每日自动化样例（未部署）

定时器必须先停止应用写入，再执行备份，失败以非零退出码和状态 JSON 交给现有监控/告警；不得把“脚本启动成功”当作备份成功。下面只是交给运维的样例，不包含主机名、账号、密钥或真实 age recipient：

```ini
# /etc/systemd/system/sunjack-backup.service
[Unit]
Description=SUNJACK ERP quiesced database and private media backup
OnFailure=sunjack-backup-alert@%n.service

[Service]
Type=oneshot
WorkingDirectory=/srv/sunjack/current/backend
ExecStartPre=/usr/bin/systemctl stop sunjack-web.service
ExecStart=/srv/sunjack/venv/bin/python manage.py create_consistent_backup --database /srv/sunjack/data/app.sqlite3 --media-root /srv/sunjack/private-media --output-dir /srv/sunjack/backups/local --quiesced --encrypted-output /srv/sunjack/backups/offsite/latest.age --age-recipient <managed-public-recipient> --status-file /srv/sunjack/backups/status/latest.json
ExecStopPost=/usr/bin/systemctl start sunjack-web.service
WorkingDirectory=/srv/sunjack/current/backend
```

```ini
# /etc/systemd/system/sunjack-backup.timer
[Unit]
Description=Daily SUNJACK ERP backup

[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true

[Install]
WantedBy=timers.target
```

在 PostgreSQL 生产部署中，上述 `--database` 不能直接套用 SQLite 命令。运维必须使用已验证的 PostgreSQL 归档/快照适配器，并把数据库、媒体和清单放入同一一致性归档；当前仓库没有这个可执行生产适配器，也没有运行真实 PostgreSQL。

## 加密副本与故障域

`--encrypted-output` 只接受 age 公钥 recipient，并调用环境中受管控的 `age` 可执行文件；私钥不进入仓库、命令行或状态日志。当前开发机没有已核验的独立异地存储和生产密钥管理，因此不能把本地 ZIP 或模拟 age 调用写成加密异地备份 PASS。目标环境需证明：本地副本与加密副本位于不同故障域、管理员最小可读、复制成功可检测、恢复时可取得私钥且轮换不丢失历史副本。
