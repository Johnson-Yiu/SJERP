## 附件访问与处置规则

- 现有私有媒体 API 和银行凭证下载 API 保持原有授权、业务记录/来源绑定、完整性校验及原文件名机制。本包没有重建银行凭证下载接口。
- 文件是否可内联由读取后的实际字节经图像解码验证；只允许 PNG、JPEG、GIF、WebP。客户端扩展名、上传 MIME 和历史保存的 `content_type` 不决定预览类型。
- SVG、HTML、文本、PDF、未知格式及损坏图像均以 `application/octet-stream` 和 `Content-Disposition: attachment` 返回，并设置 `nosniff`、私有缓存控制、同源资源策略、CSP sandbox 和 no-referrer。该规则在每次读取时作用于已有旧附件。
- 缺失、损坏、无权读取或不可访问的附件给普通用户统一提示“附件当前不可访问，请联系管理员核查。”，不返回存储路径、散列或异常栈；详细诊断只进服务端日志。
- 业务页面契约（交 A/B/D 接入）：私有文件仍通过 `/api/media/<relative_path>` 授权读取；调用方不得根据上传 MIME 自行内联预览。只有响应声明并实际呈现允许的已验证栅格图像时才提供预览；其他文件按下载处理。银行凭证继续调用现有 `/api/finance-ledger/voucher-download/`。

## 运行环境核对

仓库目标拓扑为 Nginx → Gunicorn/Django → PostgreSQL，并使用独立持久化私有 `MEDIA_ROOT`。`start-main-worktree.ps1` 启动的是本机开发服务（Django `runserver` 回环 8100、Vite 回环 5191），不能作为正式服务证明。

本机只读探测曾观察到 `127.0.0.1:8100` API 与 `127.0.0.1:5191` 前端返回 HTTP 200。监听进程的命令行/加载代码 SHA 无法读取，因此没有把文件版本或进程启动时间作为候选 SHA 证明。`192.168.1.79:8443` 的 HTTPS 探测失败，且该端口进程未能确认属于 ERP，故不作服务归属判断。

## 可执行运行与恢复说明

SQLite 维护脚本要求先停止 ERP 写入并明确传 `--quiesced`。PostgreSQL 使用独立维护适配器和受控配置，不能把 SQLite 命令套用于 PG。当前目标服务器、正式调度器、异地副本和凭据均未提供/不可访问，因此没有启动正式调度、修改生产 ACL 或连接真实业务库。

恢复必须选用新的、原本不存在的隔离目标；失败重试使用另一个新目标。工具先在同文件系统临时区解包并校验路径、归档完整性、数据库、配置和媒体摘要，再原子提交。不得把业务服务器或正式媒体目录作为演练目标。具体命令、配置白名单和权限要求见 [ISS-018 数据库与附件一致性备份恢复运行手册](../../deployment/ISS-018-数据库与附件一致性备份恢复.md)。
