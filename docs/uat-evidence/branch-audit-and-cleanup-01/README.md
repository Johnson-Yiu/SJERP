## 分批处置

1. **批次 1，66 个祖先分支候选。** 逐行读取候选 TSV。重新执行 `git ls-remote --heads origin refs/heads/<branch>`，必须与表中完整 SHA 一致。用 `git merge-base --is-ancestor <sha> <current-master>` 复核可达。刷新开放 PR 的 head/base、同分支 CI、两仓库工作树、远端保护规则、试点脚本或文档及外部消费者。任一项有冲突就移入保留批。保存执行前快照和结果，获清理授权后按单分支、明确 ref 执行。
2. **批次 2，33 个补丁或当前终态候选。** 完成批次 1 的检查，另复核当前业务是否有后续回退、重实现或测试覆盖差异。先在独立恢复仓库保存分支完整 SHA 和 Git bundle，通过演练恢复并对照清单，再决定是否提交单分支清理。原分支涉及分叉迁移或当前工作时继续保留。
3. **保留批，177 个远端分支。** 包括 master、发布和认证引用、开放 PR、检测到本机或运行关联的分支、B 类和 D 类。先完成待整合表中的独有运维入口与交接文档，再盘点历史证据与重点业务差异。D 只在补齐明确的后继、验收或业务决定后改变分类。
4. **本地工作树。** 暂无可执行移除清单。先逐树核对工作、服务、分离提交、未跟踪与忽略文件、数据库及媒体引用。独有内容需做受保护归档并实际恢复验证，确认旧共享对象库及重建依赖不再使用后，再评估正常移除。含扫描异常、在用链接、备份未通过或归属不清的工作树继续保留。

审计分支提交仅新增本目录文档和索引。清理候选表是后续执行输入，本轮未执行任何清理。
