## 调用边界

历史导入不得直接写资金事实、分配、核对、审批或审计表，也不得调用绕过权限和来源校验的 ORM 批量写入。现有历史预检是只读流程，不创建或确认资金。未来承接服务需要在单一事务内校验权限、身份、来源、凭证、冲突及额度，并追加审计；只有已确认的银行真实事实才能影响实际资金口径。开发超级管理员不能冒充两个真实审批人。

## 必须保留的输入事实

- 原系统标识与来源记录键：明确作用域及唯一性，同一键和规范化内容可安全重试，不同内容冲突须拒绝。
- 真实性：真实、模拟、待核实分别保留；模拟和待核实不改变正式余额、订单余额、自动核销或实际资金统计。
- 银行或现金账户：只能绑定经明确核实的受控账户，不能从显示名称推测所有权；旧账户映射不唯一时转人工核实。
- 银行实际发生日期、方向、实际人民币金额、币种精度与来源关联；缺失不得以订单日期、系统时间或外币参考汇率猜补。
- 文件凭证的受控私有文件标识及系统读取计算的摘要；人工手填 SHA 仅作为声明，不是文件校验成功。保留原始来源及更正链，不覆盖已确认事实。
- 发起、复核、确认、撤销或更正各自的真实身份、原因与时间；按已确认规则需要两人审批时不得自批。

## 当前兼容性事实

当前 `RmbCashEvent` 和 `CashSourceAllocation` 由 `crm.services.cash_events` 提供登记/确认流程，要求受控账户、来源分配、幂等请求键和财务数据权限。`evidence_sha256` 现为人工声明，不能证明文件已经读取。现有已确认资金不可直接覆盖或删除；未知来源及相关退款保护继续 fail-closed。现有 API 的实际统计为已登记且已确认的银行事实，不代表全部账户余额。扩展前应保持历史账面折算参考及既有分配额度、重复候选和并发保护。

## 落地与联调门槛

资金包需先实现并测试受控文件绑定、真实身份与复核、账户及来源表示、请求幂等和事务审计，再发布版本化服务签名、输入输出/错误契约、权限矩阵和合成调用测试。应分别验证重复键异内容、权限拒绝、凭证缺失、事务失败、真实 PostgreSQL 并发和原业务表不变；合约未完成前，历史迁移包仅可维持只读预检。
