# 资金承接服务 v1

适用源码：本工作包 `codex/finance-closeout-batch-20261104`。统一起点 `4388947d70d26bca66ca0bfc76b2383a2fc0d404`。最终提交以交付 SHA 为准；旧 `CONTRACT-DRAFT.md` 是此前未实施时的历史草案。本接口已实施，但没有授权历史迁移执行器或真实历史导入。

## 写入入口与权限

历史迁移包不得直接写 `Finance*`、`RmbCashEvent`、来源分配或审计表。承接通过 `crm.services.finance_closeout.submit(payload, authenticated_user)`；审批用 `approve(id, reviewer)`，实际记账用 `post(id, operator, voucher_checked=True)`。HTTP 对应 `/api/finance-ledger/instructions/`、`approve/`、`post/`。只有实际记账建立 `FinanceFact`；保存、预检和批准不等于发生资金。

新公司账户流程要求财务/流水查看及相应写权限和全局财务数据范围；关联订单还检查原业务模块权限。不是把有采购权的人员扩成可读全部财务。旧银行事件继续按原来源整批可见性控制。开发超级管理员仍复用服务端入口；开发身份记录为开发身份，不能当成两个真实审批人。隔离测试账号是真正认证的合成用户，未启用正式 RBAC。

## 输入格式

金额使用精确十进制字符串，仅 CNY 实际金额，最多两位；正常金额为正，独立基准和核实更正允许零。日期显式输入 `YYYY-MM-DD`，不得从订单日、系统日或参考汇率猜补。`source_system` 与 `source_key` 标识可核实的原始来源；同一原始记录不能换请求键重复计入。一次业务操作的 `request_key` 必须持久保留。

```json
{
  "request_key": "SYNTH-MIGRATION-0001",
  "kind": "cash",
  "account": 1,
  "voucher": 1,
  "actual_date": "2026-02-02",
  "amount": "100.00",
  "direction": "income",
  "nature": "unclassified",
  "truth": "needs_verification",
  "source_system": "SYNTH_LEGACY",
  "source_key": "SYNTH_ORIGINAL_0001",
  "reason": "仅合成承接示例；真实资料和账户尚未核实",
  "allocations": []
}
```

该示例的账户、凭证编号必须由隔离调用方先建立，不能照抄为真实资料；`truth=needs_verification` 只能保存待处理指令，不能批准或计入实际资金。其他真实性值是 `verified`、`simulated`；模拟同样不能记实际资金。“预检通过”不是已审批或已承接。

可选关联为 `parent`（新账户事实）、`legacy_parent`（已明确映射的原银行事件）、`approval`（退款批准指令）、`replaces`（已取消或核实失败的旧指令）。`parent` 与 `legacy_parent` 不得同时填写。修订使用新的操作请求键和可追溯来源键，原指令不覆盖，敏感操作重新复核。`allocations` 为 `[{"order": 1, "amount": "30.00"}]`，不可重复订单或超总额；实际退款还检查逐订单批准份额，归属不清留空并保留待分配。

## 账户、文件与实际发生

- `/accounts/` 明确银行/现金、自有/外部/待核实；名称不确定归属。未使用账户的待定归属通过 `/verify_account/` 留痕核实；已有历史不能直接改写。`/mappings/` 显式承接旧受控银行标识，不自动猜同名，不把旧银行映射成现金。
- `/vouchers/` 受控上传 PDF、PNG、JPEG，合计最多10MB，流式拦截超限返回413。返回系统读取文件计算的摘要及私有ID；不返回存储URL。每次记账和下载重新核对文件摘要及大小。文件摘要不是银行真伪认证，仍需人工核实。
- 银行旧入口另用 `/api/rmb-cash-events/voucher-upload/`，表单字段 `file` 和 JSON 字符串 `sources`；文件绑定完整来源集合。登记可带 `private_voucher`，原待确认草稿可调用 `/{id}/bind-voucher/`。新确认缺实际文件、来源不符或文件篡改均拒绝。原已确认历史不重写，未绑定文件的历史声明明确标记 `historical_manual_reference_only`，不会自动升级为文件核验。
- 文件下载只经业务鉴权的下载动作，`private, no-store`、附件响应；`/media` 不能公开访问凭证。银行范围文件不混入全局账户凭证列表。

## 资金操作语义

| kind / 动作 | 语义 |
|---|---|
| `cash` | 独立、已核实实际收支；性质可以待分类，仍计入实际变动。不是第二笔业务收款，不核销订单。 |
| `opening` | 独立基准，须另一人复核；为该日期开始时点余额，当日及之后变动另计。不作为收入，不配置全公司启用日期。 |
| `correction` | 须另一人复核；填写核实后的完整金额、方向、实际日期，**不是差额付款**。原版本保留；有效版本用于统计和余额，零更正不制造实际流量。存在已退款、本金关联或其他后续时安全拒绝直接覆盖基础，不能自动解除来源。 |
| `refund_approval` | 另一人批准的商业退款依据，可凭明确依据超过原收款；批准本身无实际流出。需 `excess_reason`。 |
| `refund_payment` | 关联有效批准，实际文件、日期和扣款金额；仍须另一人复核。累计不超过批准额、逐订单不超过份额；跨批准累计相对原有效收款的超额通过 `excess_amount` 单列。 |
| `bank_return` | 关联明确的新/旧原实际事实，反向实际变动，累计不超过尚未退回金额；不改原事实或释放业务来源额度。 |
| `refund_return` | 扣款后退回为另一笔实际事实，原扣款仍保留；不把批准未扣款或失败当作支出。 |
| `/fail/` | 仅明确核实未实际扣款可标记失败，须 `no_debit_confirmed=true` 及原因；结果未知不能假定失败重做。重试为新修订并按规则重审。 |
| `/transfers/` | 显式指定两端，允许跨日；本金相同、方向相反、不同自有账户，手续费另记。未匹配不隐藏本金。既有银行用 `legacy:编号`，新事实用 `fact:编号`；历史匹配另需两端受控文件，原银行事实不复制。 |
| `/reviews/` | 逐账户期间、对账单、余额、差异、处理说明、人和时间；差异非零不能完成。新增迟到事实或更正后指纹变化，返回 `needs_review`，旧核对记录保留。 |

`cancel/` 只取消尚未记账的指令并追加原因；不能删除或直接冲销已记账历史。已核实转账本金及已有退款依赖不能通过普通分类/直接改写改变其核实基础。上述拒绝属于防止猜测历史事实的保护，不自动调整采购、销售、库存、银行付款或订单余额。

## 幂等、事务与统计

同键同规范化内容返回原指令；异内容409。不同操作键允许合法同额业务，但同原始来源只能记一次。疑似同账户日期方向金额须使用当前候选令牌和人工说明，不自动去重；旧银行候选有隐藏来源时不放行。确认再次执行返回同一事实；PostgreSQL 账户/指令/父事实锁及数据库唯一约束防并发重复或超额。关键写入和追加 OperationLog 同事务；审计失败回滚全部业务副作用。开发审计的 operator 为空、元数据显式标记开发身份，不能伪造员工。

`/finance-ledger/facts/` 保留账户原始明细及有效公司流量标志，支持 CSV。原实际资金 API、财务概览及 `actual_cash` 报表聚合相同有效事实：基准排除、已核实本金排除、更正使用有效版本、银行与现金分项。旧 `cash` 账面人民币折算及核心业务表保持原口径。余额只有明确基准和账户映射时才能复算，不宣称已覆盖全公司。

## 返回和拒绝

HTTP 登记201/幂等重放200，正常动作200或201；400是规则/文件/精度/来源校验，403是权限，404是不可访问或不存在，409是请求内容/来源/重复核实冲突，413是文件超限。拒绝不产生部分资金、额度释放或第二条业务操作审计。迁移包须保存请求键及原结果，响应未知先按已存指令核查，不能换键盲目重做。
