## 代码核对

1. **有效分类用于两类本金匹配。** `finance_closeout.py:523-526` 的 `effective_nature()` 取 append-only 分类中最高主键的最后一条；这与 API `fact_data()` 和 `reporting_events()` 展示/汇总有效分类的规则一致（`finance_closeout_api.py:48-60`、`finance_closeout.py:569-592`）。`match_transfer()` 与 `match_historical_transfer()` 都使用该值，因此事实原始 `nature=internal_principal` 后追加 `expense` 分类时，两条匹配入口均拒绝将其当作内部本金。

2. **锁后复核与受支持写入路径协调。** `match_transfer()` 先锁相关账户，再重新取得并锁事实，然后检查方向、有效分类、冲销及既有匹配（`finance_closeout.py:470-494`）。`classify()` 也先锁同一账户，并拒绝已匹配事实的重新分类（`498-510`）。`match_historical_transfer()` 锁两端账户及对应事实/旧银行事件后，再复核新事实的有效分类与冲销状态、旧事件的冲销状态（`600-654`）。受支持的分类、冲销和匹配因此共享账户锁域；静态路径未发现锁顺序绕过。

3. **指纹按核对截止日跟踪匹配。** `balance()` 只取 `actual_date <= end` 的新事实及 `bank_date <= end` 且不早于启用基准的旧银行事件，再把这些端点关联的两类匹配 ID 纳入指纹（`514-555`）。发生在核对截止日后的纯新事实匹配不会进入该截止日指纹；若历史匹配触及截止日前已纳入余额的旧事件，则会改变指纹。匹配不改变账户金额，已提交测试也断言了这一点。

4. **旧核对的兼容是有条件的。** 无任何匹配的旧账户沿用原四字段摘要，测试 `test_unmatched_review_fingerprint_remains_compatible` 验证了该路径（新测试文件 `114-120`）。但新逻辑只在存在匹配时添加 `transfer_matches` / `historical_transfer_matches` 两个键。旧版本保存的摘要没有这些键，因此已有任一匹配的账户在升级后会得到不同指纹，API 将其状态显示为 `needs_review`（`finance_closeout_api.py:103-110`）。这是可预期的保守行为，但当前没有报告/测试说明其是否为有意的一次性重新核对要求。
