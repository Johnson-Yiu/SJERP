# R1-ISS-021-AUDIT-01 正式销售订单数量变更影响审查

状态：`AUDIT ONLY / BLOCKED FOR IMPLEMENTATION / CI PENDING`

审查分支：`codex/r1-iss-021-audit-01`

审查基线：`origin/master`，`25405e1b25ff8a218b67883acf489ada8a53e146`

本轮没有修改生产业务模型、服务、API、前端页面或历史数据。仅增加审查专用探针 `backend/crm/tests/test_iss021_audit_probe.py`，用于在 Django 隔离测试数据库中验证当前正式订单数量变更的拒绝行为和既有事实保护。

## 结论摘要

当前实现不能完成 ISS-021 的正式销售订单数量变更：

- `OrderSerializer.validate()` 调用 `validate_contract_edit()`；正式订单的商品明细变化（包括数量）直接返回 400。
- 现有 `ContractChangeRequest` 只有合同金额 `amount_delta`、日期、说明和状态，没有原数量、新数量、数量差额、操作人/变更时间的专用数量变更结构。
- `ContractAmountAdjustments.vue` 只提供合同金额调整，不能据此认定商品数量变更已实现。
- 当前安全行为保留了订单行、发货、收款、采购和共享成本数据，但也意味着 100→150、100→60 等合法业务变化没有可用入口。

因此 ISS-021 继续保持台账状态 `BLOCKED`。不建议在现有 `PATCH /api/orders/{id}/` 上直接放开数量字段。

## 隔离业务探针

探针建立销售订单 A：SKU X `100 pcs`，并覆盖：

1. 100→150；
2. 100→60，未发货；
3. 100→60，已发货 50；
4. 100→60，已发货 70；
5. 正式采购 100；
6. 同一采购单拆分给两个销售订单；
7. 已建立应收计划并登记部分收款；
8. 多 SKU 同时提交，只调整其中一行。

实际结果：所有正式订单数量变更请求均返回 HTTP 400；原订单行仍为 100，发货 50/70 的历史数量不变，共享采购成本归属、部分收款、多 SKU 行均不发生副作用。探针未宣称当前系统支持这些数量变更，只确认现有拒绝和历史事实保护。

交易单位和库存/采购缺口的基础计算由既有 `test_trade_finance_upgrade`、`test_fulfillment`、`test_procurement` 等回归覆盖；当前数量变更本身没有 API，因此不能虚构一条“交易单位变更成功”的验收路径。

## 业务影响矩阵

| 场景 | 当前行为 | 风险结论 |
|---|---|---|
| 100→150，未采购/未发货 | 400，数量不变 | 缺少增加数量能力；实现时需增加采购缺口、预留和应收影响 |
| 100→60，未发货 | 400，数量不变 | 缺少减少数量能力；可安全允许，但必须保留原记录和审计 |
| 100→60，已发货 50 | 400，数量不变 | 业务规则允许，现有系统无法执行；新值至少应为 50 |
| 100→60，已发货 70 | 400，数量不变 | 当前拒绝是安全的；P1 必须明确拒绝原因，不得出现低于 70 的状态 |
| 已正式采购 100 后减少 | 400，采购不变 | 正确保留正式采购，但需要显示采购过剩并人工处理 |
| 已正式采购且部分到货后增加/减少 | 400，采购/到货不变 | 新数量不能覆盖到货流水；需按剩余需求重新计算 |
| 已部分收款后减少/增加 | 400，收款不变 | 已收款必须保留；减少低于已收金额需先退款或业务决定 |
| 多 SKU 只改一行 | 400，所有行不变 | 新服务必须按行记录，不得整单删除重建 |
| 箱/卷交易单位 | 当前正式数量无编辑入口；库存数量按基础单位 | 新入口必须由可信交易单位快照换算基础数量，处理整包装/尾差规则 |
| 一个共享 PO 服务多个订单和库存 | 采购成本归属独立守恒，销售数量不可改 | 不得因单个订单减少而自动取消 PO 或把成本静默转移；需人工例外处理 |

## 关键风险

1. **应收不一致**：`Order.total_amount` 由当前商品行实时计算，但 `ensure_default_payment_plans()` 对已有计划不会自动重建；直接改数量可能造成订单总额与应收计划不一致。
2. **已收款边界**：收款交易事实独立保留。数量减少后的新金额不能低于已收金额，若确需减少必须明确退款/冲销顺序。
3. **预留过量**：`rebalance_sku_reservations()` 能重建预留，但正式数量更新当前没有调用它；并发下直接改行可能在重算前产生短暂错误状态。
4. **采购过剩**：采购草稿和正式 PO 是独立事实；系统没有“数量减少导致采购过剩”的专门提醒、处理人和后续动作。
5. **共享成本归属**：当前校验的是采购行总量守恒，不是订单需求守恒；自动将减少量从订单 A 转给库存或订单 B 会改变成本归属事实。
6. **历史关联**：草稿更新会删除并重建订单行；正式订单不能沿用该路径，否则会破坏发货、库存、采购和审计外键关联。
7. **并发覆盖**：现有数量更新没有数量变更版本字段。新服务必须锁订单、相关订单行和受影响 SKU，并在事务内重新核验发货、收款、采购归属。
8. **快照保护**：未来整合 ISS-037 后，数量变更不得重新从客户/SKU 主档生成主体和行级历史快照。

## 分阶段建议

### P1：安全数量变更模型与历史记录

- 新增专用数量变更记录（建议保存订单、订单行、原基础数量、新基础数量、差额、原/新交易数量及可信单位快照、原因、操作人、服务器时间、状态/版本）。
- 在单事务内锁订单和订单行；用当前有效发货量拒绝低于已发货数量的减少。
- 保留订单编号和原订单行身份，不删除重建正式行；复用 `OperationLog` 记录业务动作和 before/after。
- 明确是否允许一次请求修改多行、是否要求每行原因、是否允许取消待处理变更。

### P2：库存、采购、发货一致性

- 按基础单位重新计算受影响 SKU 的预留，并保持已发货流水不可变。
- 增加采购缺口差异和“采购过剩”提醒；不自动取消/删除草稿或正式 PO。
- 对共享采购只保留现有分配，数量减少后的多余采购由人工成本归属/库存流程处理；不得自动改写其他订单或库存归属。
- 加入多 SKU、重复 SKU、箱/卷换算和并发版本冲突测试。

### P3：应收及成本一致性

- 以数量/单价/交易单位快照计算金额差额，明确税费、运费、折扣和币种口径。
- 未结清计划只能在受控规则下增加、减少或新增调整计划；已结算金额不得被覆盖。
- 减少导致新应收低于已收时，明确先退款/冲销还是禁止确认。
- 明确采购过剩和共享 PO 对销售成本、库存成本、毛利统计的处理，不在本议题自行猜定财务口径。

### P4：前端操作与完整验收

- 在正式订单工作台提供数量变更入口、原因、当前已发货/已采购/已到货/已收款影响预览和确认/取消。
- 失败或版本冲突不关闭、不部分保存；展示需要人工处理的采购过剩。
- 按正式权限测试销售、采购、库存、财务数据范围；不把前端隐藏当作后端鉴权。
- 以真实 Chrome 验收正常增加、合法减少、低于已发货拒绝、收款和共享 PO 保护。

## 需要业务负责人决定

- 数量变更是否立即生效，还是先生成待确认变更；是否保留原订单号和是否产生修订号。
- 单价、折扣、运费、税费（如未来存在）在数量变更中的金额计算口径。
- 减少后已收金额高于新订单金额时，是必须先退款/冲销，还是允许形成待处理差额。
- 已采购/部分到货的过剩数量由谁处理；是否允许人工转库存或重新分配，何时记录成本归属。
- 共享 PO 中订单 A 减少时，A 的成本归属是否保留为历史事实，还是允许在独立人工操作中改为库存/其他合法用途。
- 箱/卷等交易单位的变更输入、整包装约束、尾差和基础数量四舍五入规则。
- 同一订单并发数量变更的冲突策略，以及是否允许回溯生效日期。
