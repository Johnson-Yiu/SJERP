# 待办清单设计

状态：下一阶段设计，尚未实施。前置设计：[权限与操作记录](权限与操作记录设计-2026-09-09.md)。

目标：5 人以内团队每天能看清谁应跟进、采购、收货、发货和处理款项；完成业务时同步关闭待办。首版不建设项目管理、复杂审批或多人工作流引擎。

开发模式仍不要求真实成员登录、不创建开发人员角色；正式“我的待办”依赖内部测试阶段的真实身份。在开发阶段用隔离测试数据验证角色与分配，业务界面不冒用默认操作者姓名。

## 1. 页面与操作

新增“待办清单”入口，首页展示待办摘要及入口，保留原经营概览。

| 视图 | 说明 |
|---|---|
| 我的待办 | 当前真实成员负责且仍有业务访问权的事项 |
| 团队待办 | 负责人/管理员可见，用于分配和交接 |
| 待分配 | 责任人未设置、已停用或已无操作权限的事项；不默认推给所有员工 |
| 已处理 | 已完成/源业务取消的历史事项，保留处理依据 |

开发模式顶部显示“开发预览 · 尚未绑定真实成员”，默认团队示例/未分配视图，不声称当前人员有“我的待办”。

每项显示：事项类型、标题、源单据号、必要客户/供应商名称、负责人、截止日期、逾期情况、状态、来源数据更新时间、直接处理入口。金额、成本和联系方式按权限设计裁剪。

筛选：本人/指定负责人、状态、类型、今日到期/已逾期/本周/未设日期、关键词。默认排序：逾期 → 今日到期 → 即将到期 → 无日期，再按截止日期、创建时间排序；可标记关注，但不改变源交期。

卡片计数使用全部有权数据的服务端汇总，列表分页，不再用前 50 条或全量拉取结果充当小计。

允许操作：开始处理、记录进展/阻塞原因、设置下次提醒、跳转源业务；人工事项可完成/取消。改派受单独授权控制。自动事项不提供能改变库存或款项的“一键完成”按钮。

## 2. 两种来源

### 2.1 自动业务事项

| 规则编码 | 生成条件与粒度 | 默认责任来源 | 自动关闭依据 |
|---|---|---|---|
| customer_followup | 每客户一条，具有有效的下次跟进日期 | 客户业务负责人 | 新跟进完成原计划并更新后续日期，或明确取消跟进计划 |
| order_procurement | 每有效订单一条，SKU 汇总待采购数量大于 0 | 订单采购协调负责人 | 采购/现货分配后缺口归零，或订单取消 |
| purchase_receipt | 每已下单/部分到货采购单一条，仍有待到数量 | 采购单验货负责人；采购负责人可查看催货 | 合格到货达到应收数量，或采购单合法取消 |
| order_shipment | 每有效未发完订单一条 | 订单发货负责人 | 全部发完或订单合法取消 |
| receivable_due | 每有效待结应收计划一条 | 指定财务经办人 | 计划结清/取消；作废收款后重新进入待处理 |
| payable_due | 每有效待结应付计划一条 | 指定财务经办人 | 计划结清/取消；作废付款后重新进入待处理 |

任务立即进入列表，到期日期只影响排序与提醒，不等到逾期才生成。缺少日期保留“未设日期”，不擅自填成今天或当作未逾期即无需处理。

补充定义：

- 跟进存在客户 next_follow_up 与跟进记录 next_follow_up 两处字段。实施时统一“当前客户跟进计划”为权威入口：新建有效跟进时显式选择完成本轮并安排下一次，更新客户计划；历史文本/日期不盲目用最大日期覆盖。旧数据有冲突进入待确认，不生成多条相互冲突提醒。
- 采购缺口复用 fulfillment 服务的数量口径，按订单内 SKU 分组处理，避免重复 SKU 行重复计算采购覆盖。
- 发货任务一直存在：有合法可发数量显示“可部分发货/可发货”，尚无可发数量显示“等待到货”。不能因暂时缺货就把任务消失；是否可发仍由发货服务实时校验，不绕过其他订单预留。
- “可发数量”逐 SKU 计算本单预留与公共可用量，不把同一 SKU 可用库存重复分配到多行。付款条件仅显示计划信息，首版不凭固定定金比例自动禁止发货。
- 采购到货任务共用一个源单，不分别生成“催货”“验货”两条重复任务；采购人负责供应商跟进，验货负责人执行入库。
- 应收应付列表显示每笔计划的剩余原币及有权查看的折算金额。销售可在订单摘要跟进客户付款，但不自动取得记账权；如需分派催款沟通，另建人工沟通事项并关联订单。
- “订单待结案”暂不作为自动任务：须先明确签收、异常及合同结束规则，不能仅因已发货就自动宣布结案。

### 2.2 人工事项

用于确认样品、联系供应商补货、补齐资料等暂不能从结构化业务状态准确推导的工作。

必填标题；可关联客户/订单/采购等单据，选择负责人、截止时间、备注。不要求填写复杂优先级或工时。创建、改派、延期、完成、取消均留下记录；取消/重新打开填写原因。

有来源单据时，人工事项是沟通补充，不能代替源业务的收货、发货、记账或退款操作；无来源单据时由创建人与被分配者及负责人可见。文字与附件不得被用于绕过源单据访问限制。

## 3. 责任分配与权限

复用第一阶段 EmployeeProfile 和源单据责任关联，不再维护一份待办成员表。

- 客户跟进跟随客户负责人；订单采购协调/发货、采购验货分别使用明确责任字段。订单不能只用一个销售负责人代替所有执行角色。
- 财务使用团队配置的默认经办人，可按合同覆盖。配置是后续内测由管理员选择真实成员，不在当前开发数据库创建任何人员。
- 源责任人发生交接时，系统继承分配的自动事项同步转交；明确手工覆盖的分配必须在交接界面列出，不能静默留给离职人员。
- 分配前检查目标成员有效、具备任务所需动作，以及源对象允许的业务责任关系。分配 Todo 本身不会扩大该成员的源数据范围；需要交接源对象时，由授权负责人显式执行联合交接。
- 普通成员只能编辑自己的处理状态/备注；不能通过 PATCH assignee、creator 或 source_id 转交、冒名或移动任务。
- 负责人可改派团队任务，日志记录原/新负责人和原因。成员停用后相关事项进入待分配池，保留历史经办人，禁止自动分给姓名相同的其他成员。
- 仓库待办不展示价格；销售待办不展示采购成本；无财务查看权时，待办计数、搜索命中、标题和通知也不能泄露财务事项。

建议权限：todos.view_self、todos.view_team、todos.create_manual、todos.update_own、todos.assign、todos.view_history；同时检查源模块能力和数据范围，接口与页面使用同一规则。

## 4. 状态、延期与再次出现

| 状态 | 含义 | 转换规则 |
|---|---|---|
| open | 待处理 | 新任务/重新出现的业务条件 |
| in_progress | 处理中 | 有权经办人主动开始 |
| blocked | 有阻塞 | 填写阻塞原因；不暂停原业务交期及逾期统计 |
| done | 已完成 | 人工事项由经办人完成；自动事项由源业务条件消失而关闭 |
| cancelled | 已取消 | 人工取消需原因；自动事项只能随源业务合法取消 |

延期提醒使用 snoozed_until，与业务 due_date 分开。比如采购已逾期，即使选择明天再提醒，今天仍显示逾期。日期型任务按 Asia/Shanghai 当地日期判断：早于今天为逾期，今天为到期；不使用 UTC 截断造成前后一天偏移。

部分到货、部分发货、部分收款只更新进度，不反复关闭再新建任务。一个源条件从不成立变为成立时创建新一轮 episode；如收款作废后重新产生应收，旧完成记录保留，新轮任务链接上一轮。

跟进的“下一次”是新一轮任务而非覆盖旧完成证据；同一轮仅修改日期是延期。重复刷新、重启服务、重新同步不得额外创建新轮。

## 5. 最小数据结构（拟新增，当前不迁移）

Todo：

- kind（automatic/manual）、rule_code、source_type/source_id；自动来源使用允许列表，不接受任意模型名。
- episode、source_version/fingerprint、标题、必要摘要、due_date、snoozed_until。
- assignee、assignment_origin（inherited/explicit）、created_by；开发未绑定时允许为空并明确显示。
- status、blocked_reason、completed_at、closed_reason、version、created_at/updated_at、last_evaluated_at。
- 不在待办表复制完整财务流水、报价和客户敏感资料；显示字段在读取时按来源权限计算。

TodoEvent：记录状态、备注、改派、提醒日期、源条件关闭/再次出现等历史，关联真实人或系统身份。关键变更同时进入统一 OperationLog，共用 request_id/event_id，避免两个入口各生成一次相同业务事件。

建立自动事项唯一性约束：同一 rule_code/source_type/source_id 最多一个活动任务；历史 episode 唯一。并发写使用事务、唯一约束与版本检查，两个用户同时完成/改派不能互相无声覆盖。冲突返回 409 并提示刷新。

源对象正常被取消时任务同步取消；对象删除后保留最小来源快照和任务历史，显示“来源已删除”，不再生成死链接。

## 6. 同步策略

不引入 Celery、Redis 或通知中台。首版使用一个可重复执行的规则同步服务，结合业务提交后定向刷新与低频完整对账。

1. 订单、采购、验货、发货、计划、流水作废、责任交接成功提交后，定向重新评估有关源对象。
2. 如果提交后的刷新失败，不能回滚已经成功的付款/库存业务；记录同步错误，由补偿对账恢复。
3. 后续部署一个管理命令执行完整核对，建议每 15 分钟一次；本次不创建定时任务。时效型“今天/逾期”在读取时按本地日期计算，不依赖定时进程才能变色。
4. 每次创建/关闭任务前重新读取源状态，不直接相信过期事件中的金额/数量；过期事件不得关闭新任务。
5. 列表显示最近同步时间；跳转和执行源操作前重新检查实时数据。暂时不能评估的任务显示“状态待核对”，不被当成已完成。
6. 单条源记录异常不阻断整批同步；保留失败对象列表，由负责人查看。同步可以重复运行且不重复创建任务。

## 7. 拟定接口

| 接口 | 用途与限制 |
|---|---|
| GET /todos/ | 按本人/团队/待分配、状态、类型、时间筛选，服务端分页 |
| GET /todos/summary/ | 与列表相同数据权限和筛选，返回全部范围计数 |
| POST /todos/ | 只创建人工任务，不能伪造自动任务或系统身份 |
| GET /todos/{id}/ | 内容、源单据处理入口、当前能力、处理历史 |
| PATCH /todos/{id}/ | 白名单字段及 version；自动 due_date 不从此处改写 |
| POST /todos/{id}/start/、block/、resume/ | 更新处理进度，记录原因及真实操作者 |
| POST /todos/{id}/complete/、cancel/、reopen/ | 仅人工任务允许；自动任务提示到源单据处理 |
| POST /todos/{id}/assign/ | 授权改派，验证目标角色及源访问关系 |
| POST /todos/{id}/snooze/ | 调整下次提醒，不更改交期与逾期口径 |

不开放普通用户执行全站规则重算的接口；规则命令与系统事件使用明确 system_actor。授权失败不能通过枚举任务 ID 获取其他人员单据信息。

## 8. 提醒范围

首版只做系统内待办列表、逾期标识和首页数字，不发送邮件、短信或外部聊天消息。没有变化时不重复生成通知；人工延期不隐藏业务异常。后续若需要通知渠道，再独立确定收件人、触发条件和频率。

## 9. 验收与实施顺序

顺序：完成权限/审计 → 补责任字段和交接 → 建人工待办及唯一性 → 增加六类源规则 → 首页摘要与筛选 → 补偿对账和权限测试。当前只整理设计，待前一阶段实现后再进入开发。

必须验证的场景：

1. 同一规则同步十次只产生一个活动任务；并发同步也不重复。
2. 分批到货/发货/收款只推进同一任务；全部完成才关闭。
3. 作废收款后重新生成应收处理轮次，旧完成历史仍在。
4. 缺货时发货任务等待到货；有部分库存可部分发；不能借待办越过库存保护。
5. 取消源订单/采购单后任务同步关闭，不继续催办不存在的业务。
6. 未设日期不制造虚假逾期；午夜本地日期切换正确；提醒延期不抹去逾期。
7. 客户两处跟进日期冲突有明确处理；新增跟进后不出现重复客户待办。
8. 成员停用、角色撤销、责任交接后任务可见性和分配正确。
9. 业务人员不能通过团队视图、计数、搜索、标题或日志看到其他人的受限记录与成本。
10. 手动勾选自动事项不会把源订单标成已发货或计划标成已结清。
11. 数据超过 50 条时列表分页与摘要计数一致；访问下一页失败不显示误导性总数。
12. 业务提交成功但同步失败后，对账可恢复；旧事件乱序不把最新任务关闭。
13. 任务版本冲突提示刷新，不覆盖其他经办人的新状态。
14. 开发模式不创建真实成员、不强制登录、不伪造用户操作记录。
