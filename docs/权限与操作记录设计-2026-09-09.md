# 权限与操作记录设计

> 最新用户约定（覆盖下文原始开发阶段说明）：开发人员统一使用开发超级管理员身份，拥有全部应用功能与数据权限。已通过服务端 `development_superadmin_enabled()` 与当前身份接口实现并由侧栏展示；不逐人建号、不伪造登录、不追补正式审计。开发默认 `APP_STAGE=development`、`DEVELOPMENT_SUPERADMIN=true`，且必须 DEBUG=true、RBAC_ENFORCEMENT=false 才生效。后续进入 internal_test/production 或开启 RBAC 时开发身份失效，用户另建真实账号并分配角色。全站正式鉴权与日志仍待按本文实施，不能仅切换环境便视为已完成。持久约束见根目录 AGENTS.md。

状态：设计已整理，尚未实施或启用。适用对象：5 人以内贸易团队。

用户约束：当前为开发阶段，不给开发人员创建账号、分配角色或施加访问限制；开发完成并明确开始内部测试后，才启用真实账号、权限校验与正式操作记录。本次只提交文档，不修改业务代码、数据库、环境变量或现有权限配置。

后续待办设计见 [待办清单设计](待办清单设计-2026-09-09.md)。

## 1. 当前基础与缺口

沿用现有 Django User、EmployeeProfile、AccessRole、RolePermission、OperationLog，以及 audit.py、permissions.py 和 OrganizationPage.vue，不另建一套身份系统。

- 已有组织、岗位、角色、成员与六种基础操作权限，但模块目录未覆盖供应商、采购、包装、发货、应收应付、日志等所有实际入口。
- 默认业务接口使用 AllowAny。当前权限检查主要覆盖权限配置和部分报价导出，不能认为设置 RBAC_ENFORCEMENT 就能完整执行全站权限。
- 当前匿名操作者会显示默认姓名与“超级管理员”，只是开发展示，不能作为授权凭证或真实身份。
- 操作日志已有操作者、对象、前后数据、变更字段，但依赖真实登录与 AUDIT_LOG_ENABLED。普通模型快照不会自动覆盖订单子明细和所有关联变化。
- context 聚合详情、workbench、仪表盘、导入导出、附件和自定义动作都需要纳入权限，不能只限制导航菜单与基础增删改。

## 2. 开发与内测模式

| 项目 | 当前开发阶段 | 后续内部测试阶段 |
|---|---|---|
| 登录要求 | 保持当前开发体验 | 除登录、CSRF 初始化和最小健康检查外，业务访问要求登录 |
| RBAC_ENFORCEMENT | 保持 false | 完成验收并明确切换后设为 true |
| AUDIT_LOG_ENABLED | 保持 false | 与权限一起启用，设为 true |
| 开发人员账号/角色 | 不创建、不分配 | 不自动转为测试成员；按实际参测名单单独邀请 |
| 开发历史操作 | 不伪造、不追补正式日志 | 从启用时间起记录可验证的身份与操作 |
| 界面文案 | “开发模式 · 权限尚未启用”，明确默认姓名不是登录身份 | 显示真实成员姓名、角色及退出入口 |
| 角色模板 | 本文定义；当前不灌入数据库 | 切换准备阶段幂等初始化，实际成员由管理员明确分配 |

实施时增加部署阶段声明（建议 APP_STAGE=development/internal_test），由服务端配置决定，不能被浏览器或请求参数修改；不借用 DEBUG 作为权限绕过条件。

开发阶段两开关仍关闭。internal_test 阶段若权限/日志任一开关关闭，或仍使用开发默认密钥，应拒绝启动并提示配置原因，不静默退回匿名模式。权限开关与日志开关不能作为普通网页上的切换按钮。

内测回退方式：停止内测服务、维护数据并恢复已验证版本；不在正在使用的内测环境临时关闭鉴权来“解决访问问题”。开发人员需要排查时使用独立开发副本。

## 3. 身份与成员生命周期

- 沿用 Django session 登录；增加登录、退出、当前用户/有效权限接口。前端 Axios 配合 CSRF，所有写操作包括登录均校验 CSRF；内测使用受控部署及合适的 Cookie 设置。
- 登录失败提示不区分账号不存在与密码错误；限制连续失败尝试，不向日志写入密码、Cookie 或验证码。
- 成员停用须同时检查 User.is_active 与 EmployeeProfile.active，下一次请求立即失去访问权限，不能等旧会话自然过期。
- 角色停用、移除或权限变更在下一次请求生效；首版不使用难以失效的长期权限缓存。
- 权限依据只来自服务端真实用户，忽略客户端传来的 operator、user_id、role、权限布尔值等声明。
- 人员与角色原则上停用，不删除历史身份。日志另保存操作人姓名快照，人员改名后仍能识别历史记录。
- 保留至少一个有效系统管理员；禁止通过成员页面移除最后一位管理员或让普通管理员给自己升权。临时离职/转岗先交接单据和待办再停用，无继任者的事项进入负责人待分配池。
- 小团队可用一个公司与一个默认团队，不要求为了权限创建多层部门。现有 EmployeeProfile 的 unit/position 必填关系通过内测初始化提供默认值。

## 4. 最小角色集

以下是建议的内测默认模板，不是当前已经分配的权限。一个人可以兼任，例如“业务 + 采购”或“负责人 + 财务”。

| 角色 | 默认职责与范围 | 默认不开放 |
|---|---|---|
| 系统管理员 | 成员、角色、权限、日志与全局业务；管理内测账号 | 通过业务界面删除/篡改日志、绕过业务校验 |
| 经营负责人 | 全局业务查看、经营汇总、责任交接、业务异常及合同变更确认 | 修改系统安全配置；若需要兼任管理员，应明确分配 |
| 业务人员 | 本人负责的客户、联系人、跟进、报价、订单；查看履约进度及本单收款摘要 | 采购成本、供应商结算细节、全局财务；实际记账和作废 |
| 采购/跟单 | 所分配采购任务、供应商来源、采购单与交期；查看所需订单 SKU/数量/交期 | 客户完整跟进、销售毛利、客户收款登记 |
| 仓库/发货 | 分配到的到货/发货任务、SKU 库存、验货入库、发货、包装 | 销售价格、成本、利润、财务流水和客户完整档案 |
| 财务 | 全部有效应收应付、实际收支、核销、报表及必要合同信息 | 改写产品规格、验货发货、角色配置 |

负责人承担全部业务权限并不等于技术上自动拥有 Django superuser。两者区分，避免日常工作必须使用超级账号。

## 5. 权限判断规则

一次操作必须同时满足：有效身份 + 模块动作权限 + 目标数据范围 + 可见字段限制 + 现有业务校验。

### 5.1 基础动作与业务动作

保留 RolePermission 的 view/create/update/delete/export/import。业务动作使用附属动作授权记录（建议 RoleActionPermission，唯一键 role/module/action），不继续在 RolePermission 上增加大量布尔列。

| 业务动作 | 建议权限标识 | 建议默认角色 |
|---|---|---|
| 报价修订、备注管理 | quotes.revise / quotes.manage_notes | 业务、负责人 |
| 报价转订单 | orders.create，同时需要 quotes.view 及来源范围 | 业务、负责人 |
| 生成预计装箱 | packaging.generate | 采购、仓库、负责人 |
| 确认验货入库 | purchases.receive | 仓库、负责人 |
| 确认发货/维护实际包装 | shipments.confirm / packaging.update_actual | 仓库、负责人 |
| 手工盘点调整 | inventory.adjust | 负责人；普通仓库人员默认不开放 |
| 登记收付款，包括采购单付款入口 | finance.record_cash | 财务、负责人 |
| 核销预收预付 | finance.allocate_advance | 财务、负责人 |
| 作废实际流水 | finance.void_cash | 财务、负责人；必须填写原因 |
| 调整收付款计划 | finance.manage_plans | 财务、负责人 |
| 确认合同金额变更 | contracts.approve_change | 负责人 |
| 责任转交 | assignments.transfer | 负责人；本人不能自行转交以扩大他人访问 |
| 管理账号与角色 | security.manage_members / security.manage_roles | 系统管理员 |
| 全局查看/导出操作记录 | audit.view_all / audit.export | 管理员、负责人 |

特殊动作需要该模块的 view，但不等同于整个模块任意 update 权限。例如仓库可以 receive，不能因此修改采购价格或供应商。

导出、导入独立授权，不能因为可查看就自动允许导出。导入按目标模块权限和逐行对象范围检查，不能仅凭 imports 权限写入其他模块。自定义动作未登记映射时，在内测模式默认拒绝。

### 5.2 模块目录

保留既有模块编码与角色记录，增量覆盖 suppliers、supplier_skus、purchases、shipments、packaging、finance、payment_plans、contracts、audit、todos 等权限对象；维护唯一的服务端权限目录，前端矩阵从目录读取，不再手工维护两份。

实施时列出 urls.py 全部路由及每个 HTTP 方法、DRF action、聚合接口的权限映射。权限对象的命名可与旧 transactions/inventory 等兼容，不重复创建含义相同的 grant；旧 grant 到规范权限的转换必须显式列入迁移。

### 5.3 数据范围与兼任规则

首版只正式启用“全部”和“本人负责/分配给本人”；现有 department/department_tree 保留兼容，但组织关系与边界测试完成前不作为首批成员的默认配置。本人范围包含自己负责的业务对象和被明确分配的处理对象，而不是“自己曾创建过的所有数据”。

增加可空责任人关联：Customer、Quote、Order 的业务负责人；PurchaseOrder 的采购负责人及验货负责人；Order/Shipment 的发货负责人。使用 EmployeeProfile FK，旧 owner 文本保留为历史展示，不直接用于授权。不根据显示姓名或“Johnson”等开发默认值自动绑定账号。

- 联系人、跟进与报价通过所属客户/订单继承业务可见性；历史已独立交接的订单以自身负责人为准，不因客户转交而悄悄移动所有历史订单。
- 验货人员从专用收货 DTO 获得 SKU、数量、交期、供应商必要信息；不因此获得采购单完整价格数据。
- 销售查看订单履约摘要，不要求有供应商付款权限；采购查看订单需求摘要，不要求有客户完整资料权限。
- 商品公共基础信息可共享；成本、供应商报价、毛利等单独通过字段能力控制。只从序列化输出中移除字段仍不够：导出、聚合数字、搜索和错误消息也必须一致处理。
- 多角色权限取“满足该模块该动作的各角色授权范围”的并集。不能先把所有角色最大范围取并集再应用给所有动作，避免“全局商品查看”变成“全局客户查看”。
- EmployeeProfile.data_scope_override 只能缩小已有动作授权范围，不能创造角色未授予的动作或把 self 扩为 all；扩大权限通过明确角色分配完成。
- 没有负责人或责任人停用的记录进入负责人/管理员待分配范围，普通成员不会自动看到全部孤立记录。

字段能力建议明确登记为 catalog.view_cost（参考成本）、purchases.view_amount（采购价及合计）、orders.view_margin（订单毛利）、orders.view_receipt_summary（本单回款摘要）、finance.view_details（实际流水及结算详情）、customers.view_contact_details（完整联系信息）。字段能力仍绑定获授权源对象范围，不能被当成全局查看许可。仓库只返回验货所需数量和规格；入库实际成本默认从有权服务端采购依据取得，仓库人员不能通过提交隐藏成本字段改价。

## 6. 服务端与前端的落点

| 位置 | 实施设计 |
|---|---|
| permissions.py | 统一模式判断、角色动作判断、字段能力；移除 DEBUG 独立绕过内测权限的情况 |
| ViewSet.get_queryset | 列表、详情、搜索、选项查询统一限制对象范围，先过滤再分页与汇总 |
| 写操作服务 | 在事务内重查目标及关联对象，校验跨单据归属；批量操作逐项检查并保持已约定的原子性 |
| serializers.py | 按能力裁剪成本/毛利/敏感联系方式；只读投影用于跨部门协作 |
| context.py、workbench、dashboard | 使用相同授权策略，不通过嵌套详情、计数或汇总泄露无权对象 |
| 导入/导出 | 权限与来源范围一致；记录成功结果，不允许覆盖受保护记录 |
| 附件与媒体 | 内测私有业务附件通过鉴权下载或短期授权链接；不继续以知道静态 URL 即可获取作为保护方式。产品公开图片另行标识 |
| Django admin、管理命令 | admin 限授权管理员；业务写入同样经服务/审计。命令显式标识 system_actor，不伪造用户 |
| 当前操作者接口 | 返回模式、真实 authenticated、角色、有效模块动作/字段能力，不返回密码或安全凭证 |
| 前端 | 菜单、按钮和金额字段使用同一能力集合；403 提示无权操作，越范围对象采用 404；会话失效引导登录 |

登录成功后的页面刷新、直接粘贴 URL、修改请求中的对象 ID、手工调用接口都必须得到相同的权限结果。前端隐藏不是安全边界。

## 7. 操作记录设计

### 7.1 记录内容

沿用 OperationLog，增量增加 event_id、request_id、actor_kind（user/system）、operator_name_snapshot、outcome、reason。关联多个单据时增加日志目标关系，保存对象类型、ID、显示号和当时责任归属快照，用于订单、采购、库存、财务详情共同追溯。

每条可读记录回答：谁、何时、对哪张单、做了什么、哪些字段发生变化、为什么、关联哪些结果。

- 普通修改：记录变更字段及必要的前后值，不复制整份大对象。
- 单据修改：显式记录新增/修改/删除子明细及 M2M 关系；不能仅依赖 model_to_dict。
- 到货/发货：记录操作数量、SKU、源订单/采购单、生成的库存流水和发货单。
- 收付款：记录原币、金额、汇率、合同/计划、拆分流水；核销和作废记录分配或撤回的目标计划与金额。
- 权限与责任变化：记录原角色/新角色、原范围/新范围、目标成员及修改原因。
- 导入：父事件记录文件名、行数、成功/失败数；成功行关联业务事件，失败行保留错误类型，不把整份原文件复制进日志。
- 导出：记录对象范围、格式、结果与发起人，不将完整文件内容或临时访问地址写入日志。
- 登录成功/失败、退出、授权拒绝：使用独立安全事件通道，失败请求不伪装为业务修改成功。

禁止记录密码、口令哈希、Cookie、Token、完整会话信息；银行账号/证件等敏感值按字段白名单脱敏。URL 不保留含敏感查询参数的原文。日志接口仍按字段能力裁剪，业务人员不能通过“修改前成本”看到隐藏成本。

### 7.2 一致性与不可改写

- 正式业务修改与成功操作记录放在同一数据库事务内；日志写入失败则修改回滚，不能返回成功但没有记录。
- 信号/after-commit 不是成功业务审计的唯一落点。复杂服务中一次根操作用一个 request_id 关联多个结果，不按每个 model.save 重复记录。
- 校验失败或事务回滚不留下“修改成功”事件；拒绝/失败可另记安全事件，不包含未落库数据的虚假前后快照。
- event_id 唯一用于日志去重；request_id 仅用于关联，不能替代到货、发货、记账业务的幂等键。批量操作中的不同事件不能被误去重。
- 日志在业务 API 与 Django admin 中只读，包括管理员。删除业务对象后保留对象显示号快照；删除目标日志外键不级联删除日志。
- 数据库管理员仍具有底层维护能力，本设计不宣称具备密码学防篡改保证。日志与业务数据一起备份，内测不自动清除，后续归档政策另行决定。

### 7.3 查看入口

- 保留现有单据详情中的“操作记录”。默认展示时间、姓名、动作、摘要，点击展开有权查看的字段变化。
- 新增全局操作记录列表：按日期、人员、模块、单据号、动作、结果查询；只有管理员/负责人具有全局入口。
- 普通成员只能查看自己有权访问对象的业务记录，不因为“日志是我写的”就保留对已移交对象的永久访问。
- 已删除对象使用日志目标中的归属快照和当前角色能力决定可见性；普通成员无可靠归属证据则不展示，管理员/负责人可查。
- 开发模式日志面板显示“内部测试启用后开始记录”，不展示“暂无操作”造成正式审计已经运行的误解。

## 8. 实施顺序与启用条件

1. 完整列出路由、特殊动作、数据范围与字段映射；先补缺失模块。
2. 实现模式边界、登录与成员会话、统一权限后端；开发默认继续关闭。
3. 实现责任关联及角色模板；测试账号仅存在自动化测试数据库，不初始化到当前开发数据库。
4. 补齐 context、报表、附件、admin、导入导出等旁路校验。
