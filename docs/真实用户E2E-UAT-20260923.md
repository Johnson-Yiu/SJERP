## 2. 按提示词梳理的业务流程与覆盖结果

### 2.1 CRM 主链路

客户建立 → 联系人建立 → 客户阶段/国家信息 → 跟进记录 → 客户详情回查。

结果：已测试客户和联系人逐条创建、客户搜索、联系人回查、跟进记录保存。客户日期字段和联系人邮箱字段发现表单问题，见缺陷章节。

### 2.2 产品、SKU 与供应商链路

产品分类 → 产品建立 → 产品参数/证书 → SKU 向导 → Sales Model → 包装/交易单位 → SKU 级 SupplierSKU → 订单行供应商候选。

结果：已通过 UI 创建 50 个产品和 302 个 SKU；测试了 3 个产品的 SKU 归属、多个 Sales Model、包装和交易单位。已验证：产品级供应商并不会自动成为 SKU 候选，必须维护 SKU 级 SupplierSKU。

### 2.3 报价链路

客户 → 需求 → 新建报价 → 选择 SKU → 数量 → 单价 → 币种 → 折扣/费用 → 保存 → 状态推进 → 编辑/修订 → 接受 → 订单关联。

结果：已建立 201 份报价，覆盖 draft、sent、accepted、rejected、expired；已验证 2 个报价版本，原版本不被修订版覆盖；已验证报价到订单的关联。报价当前涉及 11 个客户和 EUR/GBP/USD 三种币种。

未完成：报价批量数据主要集中在可保存报价的国家；部分国家因国家字典校验阻塞，未能自然形成完整报价网络。

### 2.4 销售订单链路

报价/直接需求 → 订单客户 → 订单状态 → 订单 SKU 明细 → 数量/销售价/成本 → 币种/汇率 → 应收计划 → 供应商/采购 → 入库 → 预留 → 出库 → 发货 → 收款 → 成本/利润 → 完成。

结果：已逐条创建 100 笔订单，30 个客户有实际订单，覆盖 USD/EUR/GBP/CNY；订单状态真实落库为 confirmed、production、shipped。已有 2 笔报价关联订单。

注意：100 笔订单中 99 笔为单 SKU、1 笔为 2 SKU，数据多样性不足；新增订单主要停留在确认/生产中，未把每笔订单都推进到采购、入库、出库、收款和完成。

### 2.5 采购、库存、发货和财务链路

订单行供应商候选 → SupplierSKU → 采购单 → 采购成本分配 → 到货/验货 → 入库 → 库存流水 → 订单预留 → 出库 → 发货 → 应收/收款 → 应付/付款。

结果：此前已通过 UI 完成一条 2 SKU 订单的采购、成本、验货入库、库存预留、两次出库、发货、应收分次收款和供应商付款闭环；最终订单自动变为已发货，库存 purchase_in/sale_out 和财务流水可回查，金额在订单、库存、应收和财务间一致。

当前规模数据中，采购/入库/出库/发货仍只有少量真实闭环记录，未按 100 笔订单全部扩展。

### 2.6 异常、取消、回退和售后

已实际触发：缺少 SupplierSKU 候选、无效客户日期、国家不支持、直接记账金额校验失败、订单“已完成”前置条件校验、表单取消和报价取消路径。

未形成完整业务记录：库存不足占用、供应商少发/多发、损坏、部分退款、部分补发、客户取消、采购后取消、售后赔偿、售后额外物流成本、多次发货、一个采购单服务多个销售订单等。

原因：当前前端没有独立售后模块；订单“已完成”不能直接从已发货编辑表单选择，系统将已发货状态禁用并提示由出库自动更新，未找到可继续关闭订单的完整 UI 入口。

## 4. 数据修改与历史稳定性

### SKU / Sales Model 快照

修改对象：被报价、订单、库存引用的 `SKU-000001`。
修改前：Sales Model `XMBL-30K`。
修改后：Sales Model `XMBL-30K-R2`。
结果：系统生成历史版本 v1；重新打开历史订单时，订单行仍显示成交时的旧 Sales Model、旧描述和供应商快照，未被当前 SKU 主档覆盖。该项通过。

### 已验证的副作用检查

- 历史订单仍可搜索、打开和显示订单行。
- 报价修订没有覆盖原始报价。
- SKU 修改没有使历史订单行消失。
- SupplierSKU 缺失只影响采购候选，不会自动改写 SKU 主档。

### 未完成的修改矩阵

客户名称、联系人、地址、产品名称、SKU 参数、供应商名称、采购价、包装数据等未逐项全部执行；本轮优先补齐规模门槛，因此这些项目列为下一轮回归项。

## 5. 跨模块一致性

已核对通过的闭环：

CRM → 报价 → 订单 → SupplierSKU → 采购 → 成本分配 → 入库 → 库存 → 出库 → 发货 → 应收收款 → 应付付款 → 财务流水。

该闭环以一笔 2 SKU、已收清、已发货订单为基准核对，订单金额、库存入出库数量、应收核销、应付核销和财务流水一致。

规模数据的限制：99 笔新增订单仍主要只有订单与自动应收计划，采购、库存、物流和收付款没有逐笔自然联动；因此不能把“100 笔订单已建立”误解为“100 笔订单都已完成全链路验收”。

## 6. 缺陷修复与回归（2026-09-23）

| 原问题 | 修复 | 回归结论 |
|---|---|---|
| P1：Sweden/Finland 等国家报价被阻断 | 扩展报价编号国家映射，支持本轮客户国家；客户主档也可直接使用已支持的 ISO 两位码。仍拒绝无效国家，避免编号归属不明。 | Sweden、Finland、菲律宾、`SE` 均生成正确国家段编号；保留无效国家拒绝测试。 |
| P1：美元客户在“新增记账”无法保存 | 修复直接合同收款在金额首次校验后丢失金额的问题；前端在提交前校验并序列化正数金额。 | 直接 USD 客户收款 API 回归通过，金额、客户和付款计划核销均正确。 |
| P1：订单完成/取消无 UI 闭环 | 订单工作台新增“完成订单”“取消订单”。完成动作强制核验全部发货与全部应收结清；取消动作仅允许未发生采购、发货、收付款的订单，并释放预留和未结计划。 | 已覆盖“未收齐不能完成 → 收齐后完成”及“未执行订单取消 → 计划取消”两条回归。 |
| P2：可选下次跟进日期留空报错 | 分段日期组件在不完整/清空时立即清空模型；两套通用表单把空日期显式提交为 `null`。 | 已覆盖客户已有下次跟进日期清空后可保存。 |
| P2：联系人/报价收件邮箱回查不清晰 | 客户列表增加“主联系人邮箱”列；联系人邮箱继续作为新报价默认值，报价买方邮箱保存为不可变快照。 | 已覆盖客户主联系人邮箱回查和报价收件邮箱快照保存。 |
| P2：父分类不能直接挂产品 | 分类选择器在有子级的分类旁增加直接选择按钮；点击名称仍可继续展开。 | 已覆盖父分类直接选择，后端回查主分类和分类名称一致。 |
| P2：SupplierSKU 前置条件提示不足 | 空候选和不可分配候选均明确说明必须为“当前 SKU + 当前供应商”建立并启用 Supplier SKU，并给出导航路径。 | 前端构建及回归通过。 |
| P3：开发环境无操作日志 | 维持开发身份不得伪造为正式审计操作人的项目约束；将 UI 改为明确说明“正式审计未启用”，并说明内测启用真实身份后的开启条件。 | 不改变开发超级管理员或 RBAC 行为；正式审计仍需在内测环境按既定流程启用。 |

### 仍需单独立项的业务能力

售后（补发、赔偿、退款、售后成本）与异常履约不是现有模块中的一个缺陷开关，而是尚未设计的独立业务域；其会影响库存、应收应付、退款凭证和成本归属。为避免在没有规则的情况下写入错误财务数据，本次没有臆造售后账务流程。该项仍应作为下一项功能需求完成业务规则确认后实现。

## 7. 更新后的结论

数量门槛已达到：50 客户、30 个成交客户、201 报价、100 订单、50 产品、302 SKU；所有这些业务数据均通过 Browser 前端逐条创建，未使用 API、SQL 或导入绕过 UI。

系统目前可以承接：客户与联系人维护、报价及报价状态、报价修订、基础订单建立、多币种订单、供应商 SKU 候选、采购入库、库存出入库、发货、应收登记、供应商付款和基础财务回查。已有一条真实的 2 SKU 订单完成了跨 CRM/报价/订单/采购/库存/发货/财务闭环，历史 SKU 快照也验证通过。

修复后，报价国家、直接 USD 收款、订单关闭/取消、可选日期、联系人及报价邮箱、父分类选择和 Supplier SKU 提示均已有实现与回归覆盖。

系统目前仍不能据此判定为可完全依赖的生产系统，主要原因是：

1. 售后没有独立前端业务入口，补发、赔偿、退款和售后成本尚不能形成完整闭环。
2. 新增 100 笔订单没有全部自然产生采购、入库、出库、物流和收付款链路，跨模块一致性只能对已完成的小规模闭环确认，不能外推到全部订单。
3. 本轮浏览器控制连接不可用，修复后的真实浏览器 UAT 需要在连接恢复后补跑。

建议下一轮先确认售后业务规则，再用 10～20 笔订单专门构造部分付款、部分发货、少发、多发、损坏、退款和多采购单场景，执行真实浏览器全链路回归。
